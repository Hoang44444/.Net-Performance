MUST KNOW

Value Type vs Reference Type · Stack vs Heap · Object Lifetime

Concept

Value type (struct, int, bool...) chứa dữ liệu trực tiếp; gán hoặc truyền tham số là copy toàn bộ giá trị. Reference type (class) chứa một con trỏ tới object nằm trên heap; gán là copy con trỏ, không copy dữ liệu. Stack là vùng nhớ LIFO, cấp phát/giải phóng gần như miễn phí (chỉ dịch chuyển stack pointer). Heap là vùng nhớ được quản lý bởi GC, cấp phát tốn kém hơn và phải được dọn dẹp.

Mental Model

Stack = ngăn kéo bàn làm việc, mở/đóng tức thì, biến mất khi method return. Heap = kho hàng chung, mọi request đều phải "xin phiếu" (allocation) và có nhân viên dọn kho (GC) chạy nền để thu hồi phiếu không dùng nữa. Local value type sống trên stack của frame hiện tại; khi frame pop, nó biến mất không cần GC. Object của class luôn nằm trên heap, dù biến tham chiếu tới nó có thể nằm trên stack.

Ví dụ
struct Point { public int X, Y; }
class PointRef { public int X, Y; }

void Demo() {
    Point a = new(){ X = 1 };
    Point b = a;      // copy toàn bộ struct — b.X đổi không ảnh hưởng a.X
    b.X = 99;

    PointRef c = new(){ X = 1 };
    PointRef d = c;    // copy con trỏ — d và c trỏ chung 1 object trên heap
    d.X = 99;         // c.X cũng thành 99
}
Experiment

Viết 2 method: một dùng struct Point3D chứa 3 double, một dùng class Point3D giống hệt. Gọi mỗi method 10 triệu lần trong vòng lặp tính tổng khoảng cách. Quan sát Gen0 GC count bằng dotnet-counters — bản class sẽ tạo hàng chục triệu object, bản struct thì không allocation nào trên heap nếu không bị boxing.

Benchmark

Dùng BenchmarkDotNet so sánh struct nhỏ (≤16 byte) vs class tương đương trong vòng lặp copy dày đặc. Bật [MemoryDiagnoser] để thấy cột Allocated — class luôn > 0 bytes/op, struct nhỏ thường bằng 0.

Profiling

dotnet-counters monitor --counters System.Runtime để xem gen-0-gc-count tăng nhanh thế nào khi đổi struct → class. Đây là bài học đầu tiên: allocation rate là chỉ số quan trọng hơn "code trông gọn hay không".

Optimization

Dùng struct cho dữ liệu nhỏ, bất biến, hay được copy (Vector2, Point, Money). Tránh struct lớn (>24-32 byte) vì copy trở nên đắt hơn cả việc trỏ tới heap. Tránh struct có field mutable public — dễ gây bug logic khi copy ngầm.

Exercise

Viết hàm tính tổng của 1 triệu Vector3: một version dùng struct, một version dùng class. Đo thời gian và allocation của cả hai, giải thích chênh lệch bằng đúng thuật ngữ stack/heap.

SHOULD KNOW

Boxing & Unboxing

Concept

Boxing là quá trình wrap một value type vào một object heap-allocated để nó có thể được dùng ở nơi cần object hoặc interface reference (ví dụ ArrayList, object obj = 5;). Unboxing là lấy giá trị ngược lại, kèm kiểm tra type an toàn.

Mental Model

Boxing giống như bạn phải "đóng gói" một viên gạch (value type) vào một cái hộp có nhãn (object header + type info) chỉ để đưa nó qua một cánh cửa chỉ nhận hộp (tham số kiểu object). Mỗi lần đóng gói là một allocation heap mới, dù giá trị bên trong chỉ là 4 byte.

Ví dụ
int i = 42;
object boxed = i;         // boxing — allocation trên heap
int back = (int)boxed;  // unboxing

// bẫy kinh điển: non-generic collection
ArrayList list = new();
list.Add(1);            // mỗi int bị box khi Add
Experiment

So sánh List<int> vs ArrayList khi thêm 5 triệu số nguyên. Đếm Gen0 collections và bytes allocated bằng dotnet-counters.

Benchmark

BenchmarkDotNet: vòng lặp gọi string.Format("{0}", someInt) (boxing ngầm với overload cũ) so với someInt.ToString() hoặc interpolated string hiện đại — kiểm tra cột Allocated.

Profiling

Trong dotnet-trace, boxing hiện dưới dạng allocation của các kiểu tên System.Int32 (hay kiểu value type tương ứng) trong GC heap — bất thường vì bình thường int không nằm trên heap.

Optimization

Dùng generic (List<T>, Dictionary<K,V>) thay vì non-generic collection. Cẩn thận với interface constraint gây boxing ẩn (ví dụ struct implement IComparable được gọi qua interface reference).

Exercise

Tìm và sửa 3 chỗ boxing ẩn trong một đoạn code cho trước (gợi ý: string.Concat(object, object), Console.WriteLine(object) với struct, non-generic interface).

SHOULD KNOW

String Immutability & StringBuilder

Concept

string là reference type nhưng bất biến (immutable) — mọi phép nối chuỗi (+) tạo ra một object string hoàn toàn mới trên heap, không sửa string cũ. Với vòng lặp nối chuỗi, đây là nguồn allocation cực lớn.

Mental Model

Mỗi lần s += "x", bạn không "thêm chữ vào cuốn sổ" — bạn photocopy toàn bộ cuốn sổ cũ, dán thêm chữ, rồi vứt cuốn cũ đi. Photocopy càng dài, chi phí O(n) mỗi lần nối, tổng chi phí vòng lặp n lần nối là O(n²).

Ví dụ
// O(n²) — mỗi vòng tạo 1 string mới
string s = "";
for (int i = 0; i < 100_000; i++) s += i;

// O(n) — StringBuilder ghi vào buffer nội bộ, resize khi cần
var sb = new StringBuilder();
for (int i = 0; i < 100_000; i++) sb.Append(i);
string result = sb.ToString();
Experiment

Chạy cả 2 đoạn trên với n = 100,000. Đo thời gian bằng Stopwatch trước, sau đó xác nhận lại bằng BenchmarkDotNet. Chênh lệch thường ở mức hàng trăm đến hàng nghìn lần.

Benchmark

Thêm biến thể thứ 3: string.Create hoặc StringBuilder với capacity định trước (new StringBuilder(expectedSize)) để loại bỏ chi phí resize buffer nội bộ.

Profiling

dotnet-gcdump trên process đang chạy vòng lặp += sẽ cho thấy hàng chục nghìn object System.String "rác" (đã bị thay thế) đang chờ GC — bằng chứng trực quan cho việc string là immutable.

Optimization

Luôn dùng StringBuilder cho nối chuỗi trong vòng lặp. Với vài phép nối cố định (không lặp), + hoặc interpolation vẫn ổn vì compiler gộp thành 1 lệnh string.Concat.

Exercise

Viết hàm build một CSV 50,000 dòng bằng cả 2 cách, đo allocation bằng [MemoryDiagnoser], viết nhận xét bằng số liệu thật, không phải "StringBuilder nhanh hơn".

MUST KNOW

Array · Collection · Generic

Concept

Array là khối bộ nhớ liên tục (contiguous), truy cập O(1) theo index, kích thước cố định. List<T> là array động, tự resize (thường x2 khi đầy) — mỗi lần resize là 1 allocation mới + copy toàn bộ phần tử cũ. Generic (<T>) cho phép compiler sinh code chuyên biệt hóa cho từng value type (tránh boxing) trong khi vẫn tái dùng code cho reference type.

Mental Model

Array giống dãy ô tủ đánh số liên tiếp — biết số ô là tính ngay được địa chỉ, không cần dò. List<T>.Add khi đầy giống việc bạn phải chuyển toàn bộ đồ sang một tủ lớn hơn rồi vứt tủ cũ — càng chuyển nhà nhiều lần (resize nhiều) càng tốn công.

Ví dụ
// tránh resize lặp lại nếu biết trước kích thước
var list = new List<int>(capacity: 100_000);
for (int i = 0; i < 100_000; i++) list.Add(i);
Experiment

So sánh new List<int>() (không capacity) vs new List<int>(100_000) khi Add 100,000 phần tử. Log số lần resize bằng cách theo dõi list.Capacity sau mỗi lần Add tăng đột biến.

Benchmark

BenchmarkDotNet cho 3 biến thể: array cố định, List không pre-size, List pre-size — so sánh Allocated bytes, con số sẽ chênh nhau rõ rệt vì mỗi resize tạo array mới và bỏ array cũ cho GC.

Profiling

dotnet-trace + phân tích allocation theo type sẽ cho thấy nhiều instance Int32[] với kích thước tăng dần (4, 8, 16, 32...) — dấu vân tay của việc resize theo cấp số nhân.

Optimization

Luôn set capacity khi biết trước số lượng. Cân nhắc Span<T>/ArrayPool<T> (Phase 1) khi cần buffer tạm không muốn GC quản lý.

Exercise

Đo số lần resize thực tế của List<T> mặc định khi thêm 1 triệu phần tử, so với growth factor lý thuyết (x2), giải thích vì sao amortized cost của Add vẫn là O(1).

SHOULD KNOW

Delegate · Lambda · Closure Allocation

Concept

Delegate là một object heap-allocated trỏ tới method. Lambda capture biến bên ngoài (closure) buộc compiler sinh ra một class ẩn để giữ các biến đó — mỗi lần lambda được tạo trong vòng lặp là một allocation object closure mới, trừ khi compiler nhận ra có thể cache lại (lambda không capture gì / capture static).

Mental Model

Lambda không capture gì giống một "hàm tĩnh" — chỉ tạo 1 lần rồi tái dùng mãi mãi. Lambda có capture biến local giống một "phong bì" đóng gói theo các biến đó — mỗi vòng lặp tạo phong bì mới nếu biến capture thay đổi theo scope của vòng lặp.

Ví dụ
// KHÔNG capture — compiler cache delegate, 0 allocation lặp lại
list.Where(x => x > 0);

// CÓ capture biến local "threshold" — allocation closure mỗi lần gọi hàm chứa nó
int threshold = GetThreshold();
list.Where(x => x > threshold);
Experiment

Viết method gọi list.Where(x => x > threshold) trong vòng lặp 1 triệu lần, so với list.Where(x => x > 0) (constant). Đo allocation bằng [MemoryDiagnoser].

Benchmark

Thêm biến thể dùng static local function hoặc truyền threshold qua tham số method thay vì capture, xác nhận allocation về 0.

Profiling

dotnet-gcdump sẽ show các object có tên dạng <>c__DisplayClass... — đây chính là closure class compiler tự sinh, dấu hiệu nhận biết capture allocation trong trace thực tế.

Optimization

Đánh dấu lambda là static (C# 9+: static x => x > 0) khi không cần capture — compiler sẽ báo lỗi nếu bạn lỡ capture, giúp catch bug hiệu năng ngay lúc compile.

Exercise

Refactor một LINQ pipeline có 3 lambda capturing biến ngoài thành dạng không capture (dùng static lambda hoặc tham số hoá), đo lại allocation trước/sau.

MUST KNOW

Exception Cost & IDisposable / using

Concept

Throw exception không rẻ: JIT phải capture stack trace, unwind stack qua nhiều frame, và (nếu lần đầu throw ở method đó) có chi phí JIT bổ sung. Dùng exception cho control-flow bình thường (validate input) là anti-pattern hiệu năng nghiêm trọng. IDisposable/using đảm bảo giải phóng unmanaged resource (file handle, socket, DB connection) ngay khi ra khỏi scope, không đợi GC.

Mental Model

Exception giống việc gọi cứu hoả cho một sự cố — tốn kém, chỉ nên dùng cho tình huống thật sự bất thường. Dùng nó để kiểm tra "user có nhập số âm không" giống gọi cứu hoả để hỏi giờ. IDisposable giống việc trả chìa khoá phòng khách sạn ngay khi checkout, thay vì để lễ tân (GC) tự đi thu dọn sau.

Ví dụ
// XẤU: dùng exception cho control flow
try { return int.Parse(input); } catch { return 0; }

// TỐT: TryParse không throw
return int.TryParse(input, out var v) ? v : 0;

using var conn = new SqlConnection(cs); // Dispose tự động khi ra scope
Experiment

Benchmark int.Parse trong try/catch với 50% input invalid, so với int.TryParse. Chênh lệch thường là 100-1000 lần khi exception thực sự được throw.

Benchmark

BenchmarkDotNet đo riêng "throw path" vs "no-throw path" của cùng 1 method — quan sát cột Mean tăng vọt chỉ ở nhánh có throw.

Profiling

dotnet-trace có thể bắt Exception ETW event — đếm số exception/giây trong production là một early-warning cho code path lẽ ra không nên throw thường xuyên.

Optimization

Dùng TryXxx pattern cho parse/lookup. Reserve exception cho lỗi thật sự exceptional (mất kết nối DB, file không tồn tại ngoài dự kiến). Luôn using/await using cho IDisposable.

Exercise

Tìm 1 API nội bộ đang dùng try/catch để validate input, viết lại bằng Try-pattern, benchmark chênh lệch với input có tỷ lệ lỗi 10%, 50%, 90%.

MUST KNOW

async/await & Task — Tư duy nhập môn

Concept

Task đại diện cho một công việc có thể đang chạy, sẽ hoàn thành trong tương lai. async/await là cú pháp để viết code bất đồng bộ theo dạng tuần tự dễ đọc — compiler biến method async thành một state machine. Đây chỉ là phần nhập môn; cơ chế state machine, SynchronizationContext, ThreadPool interaction được đào sâu ở Phase 6.

Mental Model

await không "chặn và chờ" — nó giống việc bạn đặt đồ ăn ở quán rồi ngồi làm việc khác, quán sẽ gọi bạn khi đồ ăn xong (continuation), chứ không đứng ì ở quầy chờ.

Ví dụ
public async Task<string> GetDataAsync() {
    var data = await httpClient.GetStringAsync(url);
    return data.ToUpper();
}
Experiment

Gọi GetDataAsync() 100 lần song song bằng Task.WhenAll, so với gọi tuần tự bằng vòng lặp await. Đo tổng thời gian — song song nhanh hơn nhiều lần vì I/O không tốn CPU thread trong lúc chờ.

Benchmark

Chưa cần benchmark sâu ở đây — để dành cho Phase 6 với ValueTask, ConfigureAwait.

Profiling

dotnet-counters counter threadpool-thread-count khi chạy 100 request song song sẽ KHÔNG tăng theo 100 — vì I/O-bound await không chiếm thread trong lúc chờ.

Optimization

Luôn ưu tiên API bất đồng bộ (...Async) cho I/O. Không dùng .Result hoặc .Wait() trên Task — dễ gây deadlock trong context có SynchronizationContext.

Exercise

Viết 1 method gọi 5 API bên ngoài tuần tự bằng await, đo thời gian; viết lại bằng Task.WhenAll, đo lại và giải thích vì sao nhanh hơn dù cùng 1 luồng logic gọi.

MUST KNOW

Span<T> · ReadOnlySpan<T> · Memory<T>

Concept

Span<T> là một "cửa sổ nhìn vào" một vùng bộ nhớ liên tục (array, stack, unmanaged memory) mà KHÔNG copy dữ liệu và KHÔNG allocation heap — nó là ref struct nên chỉ sống trên stack. Memory<T> là bản có thể lưu trên heap/field/async state khi Span không được phép (vì ref struct không thể là field của class hay dùng qua async boundary).

Mental Model

Nếu array là cả cuốn sách, Span<T> giống một "kẹp trang" đánh dấu bạn đang đọc từ trang 10 đến trang 50 — không photocopy các trang đó ra, chỉ trỏ tới đúng vùng gốc. Slicing (span[10..50]) chỉ dịch con trỏ + độ dài, không copy.

Ví dụ
string csvLine = "123,456,789";
ReadOnlySpan<char> span = csvLine.AsSpan();
int start = 0;
for (int i = 0; i <= span.Length; i++) {
    if (i == span.Length || span[i] == ',') {
        ReadOnlySpan<char> field = span[start..i]; // 0 allocation
        int value = int.Parse(field);
        start = i + 1;
    }
}
Experiment

Viết CSV parser 2 bản: bản 1 dùng string.Split(',') (allocation một array string[] + mỗi field là 1 string mới), bản 2 dùng Span slicing như trên. Parse 1 triệu dòng, đo allocation.

Benchmark

BenchmarkDotNet với [MemoryDiagnoser]: kỳ vọng bản Span có Allocated = 0 B (hoặc gần 0, trừ chính int.Parse nội bộ), bản Split có hàng trăm KB/vòng.

Profiling

dotnet-trace allocation profiling xác nhận bản Split tạo ra rất nhiều object System.String và System.String[], bản Span thì gần như im lặng trên GC heap.

Optimization

Dùng Span cho parsing, formatting, xử lý buffer hot-path. Không lưu Span làm field của class hay dùng xuyên qua await — dùng Memory<T> cho các trường hợp đó rồi .Span lại khi cần thao tác đồng bộ.

Exercise

Viết lại một hàm parse log line hiện có (dùng Split/Substring) sang Span-based, đo allocation trước/sau trên 1 triệu dòng log giả lập.

SHOULD KNOW

ArrayPool<T> & Object Pooling

Concept

ArrayPool<T>.Shared cho thuê array đã cấp phát sẵn thay vì new T[n] mỗi lần — bạn Rent rồi bắt buộc Return (thường trong finally). Giảm áp lực Gen0 GC cho các buffer tạm dùng lặp đi lặp lại (network buffer, image processing buffer).

Mental Model

Giống thuê xe thay vì mua xe mới mỗi chuyến đi — dùng xong trả lại bãi, người sau thuê tiếp, không ai phải "sản xuất xe mới" (allocation) liên tục.

Ví dụ
byte[] buffer = ArrayPool<byte>.Shared.Rent(4096);
try {
    int read = stream.Read(buffer, 0, 4096);
    Process(buffer.AsSpan(0, read));
} finally {
    ArrayPool<byte>.Shared.Return(buffer);
}
Experiment

Xử lý 100,000 request giả lập đọc buffer 4KB: bản dùng new byte[4096] mỗi request vs bản dùng ArrayPool. Theo dõi Gen0 GC count trong dotnet-counters.

Benchmark

BenchmarkDotNet so allocation + thời gian; ArrayPool giảm allocated bytes gần về 0 sau vòng warm-up đầu (pool đã có sẵn buffer để cho thuê lại).

Profiling

dotnet-gcdump trước/sau khi áp dụng pool cho thấy số lượng object byte[] sống sót qua Gen0 giảm mạnh — ít áp lực đẩy lên Gen1/Gen2.

Optimization

Chỉ pool các buffer thực sự "hot" (dùng lặp lại tần suất cao). Luôn Return trong finally để tránh pool leak. Không giữ reference tới array đã Return.

Exercise

Refactor 1 hàm xử lý file/network buffer hiện có sang ArrayPool, viết test đảm bảo không có double-return hoặc use-after-return.

MUST KNOW

struct · readonly struct · ref struct

Concept

readonly struct đảm bảo mọi field bất biến — compiler tránh được "defensive copy" (copy ngầm khi gọi method trên struct field của 1 readonly context, vì compiler không chắc method đó có mutate hay không). ref struct (như Span<T>) chỉ được sống trên stack, không thể box, không thể là field class, không dùng qua async — đổi lại an toàn tuyệt đối về lifetime.

Mental Model

Không đánh dấu readonly trên struct giống việc để biển "có thể sửa" trên mọi món đồ — mỗi khi ai đó chỉ muốn "xem" (gọi method const), hệ thống phải photocopy phòng trường hợp họ sửa. Đánh dấu readonly là cam kết "không ai sửa được", loại bỏ nhu cầu photocopy đó.

Ví dụ
readonly struct Money {
    public readonly decimal Amount;
    public Money(decimal amount) => Amount = amount;
    public decimal Tax() => Amount * 0.1m; // compiler biết chắc không mutate → không defensive copy
}
Experiment

Tạo readonly List<LargeStruct> field trong 1 class, gọi method trên phần tử qua field đó (không readonly struct) 10 triệu lần trong vòng lặp, quan sát CPU tăng do defensive copy so với khi đánh dấu struct là readonly.

Benchmark

BenchmarkDotNet đo thời gian gọi method const trên struct thường vs readonly struct trong ngữ cảnh in parameter hoặc readonly field — chênh lệch rõ khi struct lớn.

Profiling

Disassembly (qua BenchmarkDotNet DisassemblyDiagnoser) sẽ lộ ra các lệnh copy struct (memcpy-like) xuất hiện thừa với struct thường, biến mất với readonly struct.

Optimization

Mọi struct đại diện cho giá trị bất biến (Money, Point, DateRange) nên là readonly struct. Dùng in parameter cho struct lớn truyền vào method chỉ đọc, để tránh copy khi truyền tham số.

SHOULD KNOW

ref · in · out · ref return

Concept

ref truyền tham chiếu tới biến gốc (đọc/ghi được), in truyền tham chiếu chỉ đọc (tránh copy struct lớn mà vẫn không cho sửa), out bắt buộc method gán giá trị trước khi return. ref return cho phép method trả về tham chiếu trực tiếp tới một phần tử trong bộ nhớ (ví dụ 1 phần tử trong array), tránh copy khi trả về struct lớn.

Mental Model

in giống việc đưa ai đó xem tài liệu gốc qua lớp kính (không sửa được, không cần photocopy). ref return giống việc trả lại đúng địa chỉ ô tủ thay vì bê cả đồ vật ra.

Ví dụ
public static ref int FindMax(int[] arr) {
    int maxIdx = 0;
    for (int i = 1; i < arr.Length; i++)
        if (arr[i] > arr[maxIdx]) maxIdx = i;
    return ref arr[maxIdx]; // trả về tham chiếu, không copy giá trị
}
Experiment

So sánh method trả struct 64-byte theo giá trị vs ref return tham chiếu tới phần tử trong array, gọi 10 triệu lần, đo CPU time.

Benchmark

BenchmarkDotNet + [MemoryDiagnoser]: ref return với struct lớn giảm cả CPU cycles lẫn (gián tiếp) áp lực cache do ít copy dữ liệu di chuyển qua lại.

Profiling

Dùng DisassemblyDiagnoser của BenchmarkDotNet xem assembly sinh ra — ref return sinh lệnh load địa chỉ, trong khi return-by-value sinh lệnh copy toàn bộ struct qua register/stack.

Optimization

Dùng in cho tham số struct >16 byte chỉ đọc trong hot path. Cẩn thận: in với struct KHÔNG readonly vẫn có thể gây defensive copy — kết hợp với readonly struct để tối ưu triệt để.

Exercise

Viết 1 hàm toán ma trận (Matrix4x4 struct) dùng in cho cả 2 tham số đầu vào, benchmark so với truyền theo giá trị thông thường.

SHOULD KNOW

ValueTask · IAsyncEnumerable

Concept

Task<T> luôn là 1 object heap-allocated, kể cả khi kết quả đã có sẵn (synchronous completion). ValueTask<T> là struct, tránh allocation cho trường hợp method thường xuyên hoàn thành đồng bộ (ví dụ cache hit). IAsyncEnumerable<T> cho phép await foreach stream dữ liệu bất đồng bộ theo từng phần tử, không cần buffer toàn bộ vào List trước.

Mental Model

ValueTask giống một "phiếu hẹn" có thể ngay lập tức nói "xong rồi, khỏi cần chờ" mà không cần in ra một tấm vé giấy (object) mới mỗi lần — chỉ khi thực sự phải chờ mới cần "vé" đầy đủ.

Ví dụ
public ValueTask<int> GetCachedOrFetch(string key) {
    if (_cache.TryGetValue(key, out var v))
        return new ValueTask<int>(v); // synchronous — 0 heap allocation
    return new ValueTask<int>(FetchAsync(key)); // bất đồng bộ thật
}
Experiment

Gọi hàm với 90% cache hit rate 1 triệu lần: bản trả Task<int> vs ValueTask<int>. Đo allocation — ValueTask giảm gần 90% object Task được tạo.

Benchmark

BenchmarkDotNet với tỉ lệ cache-hit thay đổi (10%, 50%, 90%) để thấy lợi ích ValueTask tăng dần theo tỉ lệ synchronous completion.

Profiling

dotnet-counters theo dõi gen-0-gc-count giảm khi chuyển từ Task sang ValueTask trong service có cache-hit cao.

Optimization

Chỉ dùng ValueTask khi method thực sự thường hoàn thành đồng bộ. KHÔNG được await cùng 1 ValueTask hai lần hay lưu lại để await nhiều lần — nó không an toàn để tái sử dụng như Task.

Exercise

Tìm 1 method cache-lookup trong project hiện tại trả về Task<T>, chuyển sang ValueTask<T>, đo allocation trước/sau với workload có cache-hit thực tế.

SHOULD KNOW

Channels & Concurrent Collections

Concept

System.Threading.Channels là hàng đợi producer-consumer bất đồng bộ, thread-safe, có backpressure (bounded channel chặn producer khi đầy). ConcurrentDictionary, ConcurrentQueue là collection thread-safe dùng lock-free hoặc fine-grained locking nội bộ, nhanh hơn nhiều so với tự lock quanh Dictionary thường trong ngữ cảnh nhiều thread.

Mental Model

Channel giống băng chuyền nhà máy có giới hạn chỗ chứa — nếu đầy, công nhân đưa hàng lên (producer) phải đợi, tránh chất đống gây tràn bộ nhớ. Lock 1 Dictionary thường giống việc mọi công nhân phải xếp hàng qua 1 cửa duy nhất; ConcurrentDictionary chia nhỏ thành nhiều cửa (striped locking).

Ví dụ
var channel = Channel.CreateBounded<int>(1000);
// producer
await channel.Writer.WriteAsync(item);
// consumer
await foreach (var item in channel.Reader.ReadAllAsync())
    Process(item);
Experiment

So sánh throughput của producer-consumer pipeline dùng lock + Queue<T> thủ công vs Channel có sẵn, với 8 producer threads / 4 consumer threads.

Benchmark

BenchmarkDotNet đo throughput (items/sec) của Dictionary + lock thủ công vs ConcurrentDictionary dưới tải 8 thread ghi đồng thời.

Profiling

dotnet-trace phân tích contention event sẽ cho thấy số lần thread bị block chờ lock giảm mạnh khi chuyển sang ConcurrentDictionary/Channel.

Optimization

Dùng bounded channel để tự động tạo backpressure thay vì unbounded queue có thể gây OOM. Chọn concurrent collection phù hợp thay vì tự chế lock quanh collection thường.

Exercise

MUST KNOW

Interlocked · lock/Monitor · Semaphore

Concept

Interlocked thực hiện phép toán atomic (Increment, CompareExchange...) trực tiếp trên CPU instruction, không cần kernel lock — nhanh nhất cho counter đơn giản. lock (compile thành Monitor.Enter/Exit) là mutex quản lý bởi CLR, có thể block thread. SemaphoreSlim giới hạn số lượng thread đồng thời truy cập 1 resource, hỗ trợ cả sync và async wait.

Mental Model

Interlocked giống một cái công tắc cơ khí không thể bị 2 người bấm cùng lúc gây sai — xử lý ở tầng phần cứng. lock giống chìa khoá phòng họp — ai giữ chìa khoá thì người khác đứng ngoài chờ. Semaphore(n) giống bãi đỗ xe có n chỗ — xe thứ n+1 phải chờ có chỗ trống.

Ví dụ
private int _counter;
Interlocked.Increment(ref _counter); // atomic, không cần lock

private readonly object _gate = new();
lock (_gate) { /* critical section */ }

private readonly SemaphoreSlim _sem = new(3); // tối đa 3 luồng song song
await _sem.WaitAsync();
try { /* work */ } finally { _sem.Release(); }
Experiment

8 thread cùng increment 1 biến 10 triệu lần: bản không đồng bộ (race condition, kết quả sai), bản lock, bản Interlocked. So sánh cả tính đúng đắn và thời gian chạy.

Benchmark

BenchmarkDotNet với [Arguments] số thread khác nhau (1, 2, 4, 8) — Interlocked scale tốt hơn lock rõ rệt khi số thread tăng do tránh được kernel-level blocking.

Profiling

dotnet-trace với contention provider đo Monitor.Contention event — số lần thread phải chờ lock, so sánh trực tiếp giữa lock và Interlocked (Interlocked có 0 contention event).

Optimization

Dùng Interlocked cho counter/flag đơn giản. Dùng lock cho critical section phức tạp hơn 1 biến. Dùng SemaphoreSlim khi cần giới hạn concurrency (ví dụ giới hạn số connection ra ngoài).

Exercise

Tìm 1 chỗ dùng lock chỉ để tăng 1 counter trong code hiện tại, thay bằng Interlocked.Increment, benchmark chênh lệch dưới tải 8 thread.

CancellationToken

Concept

CancellationToken là cơ chế hợp tác (cooperative) để báo cho 1 operation đang chạy biết nó nên dừng lại — bản thân operation phải chủ động kiểm tra token.IsCancellationRequested hoặc gọi token.ThrowIfCancellationRequested(). Không dừng thread cưỡng bức như Thread.Abort (đã bị loại bỏ vì nguy hiểm).

Mental Model

Giống việc bạn giơ biển "xin dừng" từ xa cho một đội đang thi công — đội đó phải tự nhìn thấy biển và dừng đúng lúc an toàn, bạn không thể tự tay tắt máy của họ.

Ví dụ
public async Task ProcessAsync(CancellationToken ct) {
    foreach (var item in items) {
        ct.ThrowIfCancellationRequested();
        await ProcessOneAsync(item, ct);
    }
}
Experiment

Chạy 1 vòng lặp xử lý 1 triệu item không check token vs có check token mỗi item, hủy giữa chừng — quan sát thời gian phản hồi lại (latency) từ lúc gọi Cancel() tới lúc thực sự dừng.

Benchmark

Đo overhead của việc gọi ct.ThrowIfCancellationRequested() mỗi vòng lặp so với không gọi — thường overhead cực nhỏ, không đáng lo so với lợi ích responsiveness.

Profiling

Trong ASP.NET Core, request bị client hủy giữa chừng (đóng tab) mà controller không truyền HttpContext.RequestAborted vào các call bất đồng bộ sẽ tiếp tục chạy lãng phí CPU/DB — quan sát qua log kết hợp dotnet-counters request-in-flight không giảm dù client đã ngắt.

Optimization

Luôn truyền và tôn trọng CancellationToken xuyên suốt call chain trong service bất đồng bộ, đặc biệt trong ASP.NET Core controller/handler.

Exercise

MUST KNOW

CLR · Managed Memory · Object Header & Type Info

Concept

CLR (Common Language Runtime) là "hệ điều hành ảo" quản lý execution: load assembly, verify IL, JIT compile, quản lý GC heap, xử lý exception, đảm bảo type safety. Mỗi object trên managed heap có 1 object header ẩn (8 byte trên 64-bit: Sync Block Index + Method Table pointer) đứng trước data thực — đây là lý do object rỗng vẫn tốn tối thiểu 24 byte (16 byte overhead + padding), không phải 0 byte.

Mental Model

Mỗi object trên heap giống 1 kiện hàng có tem nhãn (header) dán sẵn trước khi đóng gói ruột hàng (data) — tem nhãn cho biết "đây là loại hàng gì" (Method Table trỏ tới type metadata) để GC và runtime biết cách xử lý nó mà không cần hỏi lại.

Ví dụ
class Empty {} // object rỗng
// sizeof thực tế trên 64-bit: 24 byte (16 byte header + padding), không phải 0
Console.WriteLine(GC.GetGeneration(new Empty())); // luôn sinh ra ở Gen 0
Experiment

Cấp phát 10 triệu instance của 1 class rỗng, đo tổng heap size bằng dotnet-counters counter gc-heap-size, chia cho 10 triệu để suy ra overhead thực tế mỗi object.

Benchmark

So sánh memory footprint của 10 triệu struct rỗng trong array vs 10 triệu class rỗng riêng lẻ — chênh lệch là minh chứng trực tiếp cho object header overhead.

Profiling

dotnet-gcdump hiển thị "Retained Size" mỗi type, cho thấy rõ overhead cố định của object header cộng dồn trên số lượng lớn instance nhỏ.

Optimization

Khi cần hàng triệu record nhỏ, cân nhắc struct/array-of-struct thay vì array-of-class để loại bỏ header overhead nhân với số lượng lớn.

Exercise

Tính toán lý thuyết overhead tổng cộng nếu 1 hệ thống giữ 5 triệu object nhỏ trong cache — so sánh giữa thiết kế class-based và struct-based.

MUST KNOW

JIT — Từ IL đến Machine Code

Concept

Compiler C# (Roslyn) chỉ dịch source ra IL (Intermediate Language) — bytecode trung lập nền tảng, chưa chạy được trực tiếp trên CPU. Khi method được gọi lần đầu, JIT (Just-In-Time compiler) dịch IL đó thành machine code thật cho đúng CPU đang chạy, rồi cache lại để lần gọi sau dùng ngay bản đã dịch.

Mental Model

IL giống bản vẽ kỹ thuật viết bằng ngôn ngữ chuẩn quốc tế — chưa xây được nhà ngay. JIT là đội thi công địa phương, đọc bản vẽ và xây thành nhà thật (machine code) phù hợp với vật liệu tại chỗ (tập lệnh CPU cụ thể: x64, ARM64...). Lần đầu xây tốn thời gian dịch bản vẽ; các lần "xây lại y hệt" sau đó thì dùng ngay công trình đã có.

Ví dụ
// xem IL sinh ra: dotnet build rồi dùng ildasm/ILSpy trên .dll
public int Add(int a, int b) => a + b;
// IL tương ứng (rút gọn): ldarg.1 / ldarg.2 / add / ret
Experiment

Gọi 1 method lần đầu tiên trong ứng dụng, đo thời gian gọi lần 1 (bao gồm JIT compile time) vs lần 2 trở đi (đã cache machine code) bằng Stopwatch độ chính xác cao. Chênh lệch rõ nhất với method phức tạp.

Benchmark

BenchmarkDotNet tự động loại trừ JIT warm-up time khỏi kết quả đo (đó là lý do nó luôn chạy vài vòng "Pilot"/"Warmup" trước khi đo Actual) — đọc report để hiểu rõ giai đoạn Warmup.

Profiling

dotnet-trace với provider Microsoft-Windows-DotNETRuntime bắt được JIT compilation event, cho biết chính xác method nào được JIT lúc nào — hữu ích để phân tích cold-start latency.

Optimization

Với ứng dụng cần cold-start nhanh (serverless, CLI tool), cân nhắc ReadyToRun hoặc Native AOT (học ở card sau) để bỏ qua JIT lúc runtime.

Exercise

SHOULD KNOW

Tiered Compilation & RyuJIT

Concept

RyuJIT là JIT compiler hiện tại của .NET. Tiered Compilation chia việc dịch thành 2 tầng: Tier 0 dịch nhanh, ít tối ưu (ưu tiên startup nhanh), sau khi method được gọi đủ nhiều lần ("hot method"), runtime dịch lại ở Tier 1 với tối ưu hoá sâu hơn (inlining mạnh, loop optimization) chạy nền không chặn ứng dụng.

Mental Model

Giống việc dựng nhà tạm nhanh để ở được ngay (Tier 0), rồi nếu phát hiện đây là căn nhà bạn ở lâu dài và dùng thường xuyên (hot method), đội thi công quay lại xây kiên cố hơn (Tier 1) trong lúc bạn vẫn đang sống trong đó.

Ví dụ
// bật/tắt qua csproj hoặc biến môi trường
// DOTNET_TieredCompilation=0  → tắt, luôn dịch full-opt ngay từ đầu
// DOTNET_TC_QuickJitForLoops=0 → method có loop luôn nhảy thẳng qua Tier 1
Experiment

Đo thời gian startup và throughput ổn định (steady-state) của cùng 1 ứng dụng với DOTNET_TieredCompilation=0 vs mặc định (bật) — startup chậm hơn khi tắt, nhưng có thể nhanh hơn ngay từ đầu cho hot loop.

Benchmark

BenchmarkDotNet có job config riêng để kiểm soát tiered compilation, dùng để so sánh throughput "cold" (vài request đầu) vs "steady-state" (sau hàng nghìn request).

Profiling

dotnet-trace ghi lại rõ event method được recompile từ Tier 0 lên Tier 1 — quan sát trực tiếp cơ chế "warm up" của production service sau khi mới deploy.

Optimization

Với web service chạy dài hạn, để tiered compilation mặc định (bật) vì lợi ích startup nhanh > chi phí nhỏ ban đầu. Với batch job ngắn, cân nhắc tắt để có full-opt ngay từ instruction đầu.

Exercise

SHOULD KNOW

Inlining & Devirtualization

Concept

Inlining là việc JIT chèn thẳng thân method nhỏ vào chỗ gọi, loại bỏ chi phí call/return (stack frame setup). Devirtualization là khi JIT chứng minh được một virtual/interface call thực chất luôn gọi đúng 1 implementation cụ thể (ví dụ sealed class), nó biến virtual call (indirect, qua vtable) thành direct call — nhanh hơn và có thể inline tiếp theo.

Mental Model

Gọi method thường giống việc "gọi điện hỏi rồi làm theo hướng dẫn" — có độ trễ. Inlining giống việc bạn đã thuộc lòng câu trả lời nên làm luôn, không cần gọi điện. Virtual call giống tra một cuốn danh bạ (vtable) trước khi gọi đúng số; devirtualization là khi biết chắc chỉ có 1 số trong danh bạ nên bỏ qua bước tra cứu.

Ví dụ
sealed class FastValidator : IValidator {
    public bool IsValid(int x) => x > 0; // nhỏ, dễ inline
}
// gọi qua interface reference nhưng JIT có thể devirtualize + inline
// nếu chứng minh được type cụ thể tại điểm gọi
Experiment

So sánh gọi method qua interface reference với 1 implementation (sealed) duy nhất vs qua abstract class có nhiều subclass (JIT không thể devirtualize) — benchmark 100 triệu lần gọi.

Benchmark

BenchmarkDotNet với [DisassemblyDiagnoser] để xem đoạn assembly có xuất hiện call [vtable+offset] (virtual, chưa devirtualize) hay bị inline thẳng thành phép so sánh.

Profiling

PerfView/dotnet-trace CPU sampling cho thấy method nhỏ hot path không xuất hiện riêng trong call stack nếu đã bị inline — nó "biến mất" vào method cha, đây là dấu hiệu nhận biết inlining đã xảy ra.

Optimization

Đánh dấu class là sealed khi không cần kế thừa thêm — giúp JIT devirtualize dễ hơn. Giữ method hot path nhỏ gọn để tăng khả năng được inline (JIT có ngưỡng kích thước IL để quyết định inline).

Exercise

ReadyToRun (R2R) & Native AOT

Concept

ReadyToRun biên dịch sẵn một phần native code vào assembly lúc build (publish), giảm việc JIT phải làm lúc runtime — cải thiện startup, vẫn giữ CLR full-featured (GC, reflection...). Native AOT đi xa hơn: biên dịch toàn bộ app thành 1 executable native độc lập, KHÔNG có JIT lúc runtime, KHÔNG cần cài .NET runtime riêng — đổi lại giới hạn reflection động và một số tính năng dynamic.

Mental Model

JIT thông thường giống nấu ăn theo yêu cầu ngay tại bàn khách (chậm lần đầu nhưng linh hoạt món gì cũng nấu được). R2R giống làm sẵn phần lớn món trước, chỉ hâm nóng cuối cùng. Native AOT giống giao hẳn 1 hộp cơm đóng sẵn hoàn chỉnh — nhanh nhất để ăn ngay, nhưng không thể "gọi thêm món ngoài thực đơn" (hạn chế reflection động).

Ví dụ
// publish Native AOT

// publish ReadyToRun
dotnet publish -c Release -r linux-x64 -p:PublishReadyToRun=true
Experiment

Benchmark

Ghi lại bảng so sánh: startup time, memory footprint lúc idle, throughput steady-state — Native AOT thường thắng startup + memory, nhưng throughput steady-state có thể ngang hoặc thấp hơn JIT đã tối ưu Tier 1 với PGO.

Profiling

Dùng time (Linux) hoặc Stopwatch bọc quanh process start để đo chính xác cold-start; so sánh RSS memory qua dotnet-counters hoặc ps lúc vừa start.

Optimization

Native AOT phù hợp cho serverless/container cần cold-start cực nhanh và ít memory. Ứng dụng dùng nhiều reflection động (nhiều thư viện DI/ORM cấu hình runtime) cần kiểm tra kỹ compatibility trước khi chuyển sang AOT.

MUST KNOW

GC Fundamentals & Generations (Gen0/Gen1/Gen2)

Concept

.NET GC là generational, tracing, compacting collector dựa trên giả thuyết "generational hypothesis": hầu hết object chết trẻ. Gen0 chứa object mới tạo, được thu gom cực thường xuyên và cực rẻ (chỉ quét live object nhỏ, còn lại coi như rác toàn bộ vùng). Object sống sót qua 1 lần Gen0 collection được thăng hạng (promote) lên Gen1 — vùng đệm giữa. Sống sót tiếp lên Gen2 — nơi chứa object sống lâu dài, thu gom tốn kém nhất vì phải quét toàn bộ heap.

Mental Model

Tưởng tượng 1 văn phòng có 3 tầng lưu trữ giấy tờ. Tầng 1 (Gen0) là bàn làm việc — giấy tờ mới tới, phần lớn dùng xong vứt ngay, dọn bàn (collect) diễn ra liên tục và cực nhanh. Giấy tờ còn cần dùng được chuyển lên tầng 2 (Gen1) — kho tạm. Giấy tờ vẫn còn dùng sau nhiều lần dọn được chuyển lên tầng 3 (Gen2) — kho lưu trữ lâu dài, ít khi dọn nhưng mỗi lần dọn phải kiểm tra toàn bộ kho.

Ví dụ
Console.WriteLine(GC.CollectionCount(0)); // số lần Gen0 GC
Console.WriteLine(GC.CollectionCount(1)); // số lần Gen1 GC
Console.WriteLine(GC.CollectionCount(2)); // số lần Gen2 GC — hiếm hơn nhiều
Experiment

Viết vòng lặp tạo object tạm dùng-xong-bỏ (short-lived) 10 triệu lần, log GC.CollectionCount mỗi generation trước/sau. Quan sát Gen0 tăng nhanh, Gen1/Gen2 gần như không đổi — minh chứng generational hypothesis.

Benchmark

BenchmarkDotNet [MemoryDiagnoser] tự động report Gen0/Gen1/Gen2 collections/1000 operations — đọc cột này thay vì chỉ nhìn Allocated bytes để hiểu áp lực GC thực sự.

Profiling

dotnet-counters monitor --counters System.Runtime[gen-0-gc-count,gen-1-gc-count,gen-2-gc-count] để xem tốc độ GC theo generation realtime khi ứng dụng chạy dưới tải.

Optimization

Mục tiêu tối ưu là giảm số lượng object sống sót qua Gen0 (giảm promotion), vì Gen1/Gen2 collection đắt hơn nhiều. Object có vòng đời cực ngắn nên "chết" trong Gen0 càng nhiều càng tốt.

Exercise

Viết 1 workload có tỉ lệ object sống lâu cao (giữ reference trong List static) và 1 workload short-lived thuần tuý, so sánh tỉ lệ Gen0:Gen1:Gen2 collection giữa 2 workload.

MUST KNOW

LOH (Large Object Heap) & POH (Pinned Object Heap)

Concept

Object ≥ 85,000 byte được cấp phát trực tiếp trên LOH thay vì heap thường, và được coi như thuộc Gen2 ngay từ đầu (chỉ được quét khi Gen2 collection chạy). Mặc định LOH KHÔNG compact (không dồn lại chỗ trống) vì di chuyển object lớn tốn kém — dẫn tới fragmentation: nhiều lỗ trống nhỏ không đủ chứa object lớn mới dù tổng free memory đủ. POH (từ .NET 5+) dành cho object bị pin (ghim địa chỉ, thường dùng cho interop/native call) để GC không cần lo di chuyển chúng khi compact heap khác.

Mental Model

LOH giống 1 bãi đỗ xe container — xe container không thể "chen chỗ" như xe máy (compact khó), nên nếu 1 xe rời đi để lại khoảng trống giữa bãi, container khác không vừa khít chỗ đó dù tổng diện tích trống đủ → lãng phí không gian (fragmentation).

Ví dụ
// byte[] >= 85,000 byte → thẳng lên LOH
byte[] bigBuffer = new byte[100_000]; // LOH allocation
byte[] smallBuffer = new byte[1_000];   // heap thường (SOH)
Experiment

Cấp phát và giải phóng liên tục array 90,000 byte với kích thước thay đổi ngẫu nhiên nhẹ trong vòng lặp 10,000 lần, quan sát gc-heap-size tăng dần dù object cũ đã "chết" — bằng chứng fragmentation trên LOH.

Benchmark

So sánh cấp phát nhiều array 90,000 byte riêng lẻ vs dùng 1 buffer lớn cố định rồi thao tác bằng Span slicing bên trong — đo tổng memory footprint bằng dotnet-counters.

Profiling

dotnet-gcdump có breakdown riêng theo heap segment (Gen0/1/2/LOH/POH) — LOH size tăng liên tục mà không giảm dù đã hết reference là dấu hiệu fragmentation cần chú ý.

Optimization

Dùng ArrayPool<T>.Shared cho buffer lớn tái sử dụng thay vì cấp phát mới liên tục. Từ .NET Core 3.0+, có thể bật GCSettings.LargeObjectHeapCompactionMode = CompactOnce để ép compact LOH 1 lần khi cần (tốn kém, dùng thận trọng).

Exercise

Tìm chỗ trong code hiện tại cấp phát buffer/array ≥ 85KB lặp lại (ví dụ xử lý ảnh, file lớn), thay bằng ArrayPool, đo LOH size trước/sau bằng dotnet-gcdump.

SHOULD KNOW

Workstation vs Server GC · Background GC

Concept

Workstation GC dùng 1 heap, tối ưu cho latency thấp trên ứng dụng desktop/client. Server GC tạo 1 heap riêng cho mỗi CPU core, chạy song song, tối ưu cho throughput cao trên server nhiều core (mặc định cho ASP.NET Core). Background GC cho phép Gen0/Gen1 collection tiếp tục chạy song song với 1 Gen2 collection đang diễn ra ở background thread, giảm thời gian "stop-the-world" cảm nhận được.

Mental Model

Workstation GC giống 1 nhân viên dọn dẹp cho cả toà nhà — đơn giản, ít tốn tài nguyên khi toà nhà nhỏ. Server GC giống thuê riêng 1 đội dọn dẹp cho mỗi tầng (core), dọn song song nhanh hơn nhưng tốn nhiều nhân lực (memory) hơn — chỉ hợp lý khi toà nhà đủ lớn (server nhiều core, nhiều traffic).

Ví dụ
// runtimeconfig.json hoặc .csproj
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection> <!-- Background GC -->
</PropertyGroup>
Experiment

Chạy cùng 1 ASP.NET Core API dưới tải (dùng công cụ load test) với Workstation GC vs Server GC, đo throughput (req/s) và P99 latency của cả 2 cấu hình trên máy nhiều core.

Benchmark

Ghi lại bảng: memory footprint lúc idle (Server GC thường cao hơn do pre-allocate segment theo số core), throughput dưới tải cao, P99 latency — trade-off rõ ràng giữa 2 mode.

Profiling

dotnet-counters counter % Time in GC so sánh giữa 2 mode dưới cùng tải — Server GC thường giảm % time in GC đáng kể trên máy nhiều core.

Optimization

Server GC (mặc định trong container/K8s cần đọc đúng CPU limit, không phải CPU vật lý host) phù hợp cho API throughput cao. Container hoá cần cẩn thận: Server GC có thể tính sai số core nếu không cấu hình CPU limit đúng cách trong Docker/K8s.

Exercise

Kiểm tra cấu hình GC hiện tại của 1 service đang chạy trong container, xác nhận nó đọc đúng CPU limit (không phải số core của host machine).

GC Pause · Allocation Rate · Memory Pressure · Fragmentation

Concept

GC pause là khoảng thời gian ứng dụng bị tạm dừng ("stop-the-world") để GC quét/di chuyển object — nguồn gốc chính của latency spike khó đoán trong service .NET. Allocation rate (byte/giây) là chỉ số dự báo sớm nhất cho tần suất GC — allocation rate cao → Gen0 GC chạy thường xuyên hơn dù mỗi lần rẻ. Memory pressure là áp lực buộc GC chạy sớm hơn dự kiến khi hệ thống gần hết memory khả dụng.

Mental Model

Allocation rate giống tốc độ bạn đổ rác vào thùng — đổ càng nhanh, xe rác (GC) phải đến dọn càng thường xuyên, dù mỗi lần dọn thùng nhỏ vẫn nhanh. GC pause là khoảnh khắc "cả toà nhà phải dừng lại" để đội dọn rác làm việc an toàn.

Ví dụ
// đo allocation rate qua counter, không có API C# trực tiếp đơn giản
// dùng dotnet-counters counter: alloc-rate (bytes/sec)
Experiment

Tạo endpoint cố tình allocation rate cao (concatenate string trong loop mỗi request) và endpoint tối ưu (StringBuilder/Span), chạy load test song song, đo P99 latency — endpoint allocation cao có latency spike rõ rệt trùng thời điểm GC pause.

Benchmark

BenchmarkDotNet report allocation rate gián tiếp qua "Allocated" per operation nhân với throughput — tính ra bytes/sec để so sánh với ngưỡng gây áp lực GC thực tế.

Profiling

dotnet-trace ghi lại chính xác timestamp và duration mỗi GC pause; overlay với request latency log để chứng minh trực tiếp mối liên hệ nhân-quả giữa GC pause và latency spike trong production.

Optimization

Giảm allocation rate là đòn bẩy tối ưu mạnh nhất cho GC: dùng struct/Span/ArrayPool đã học ở Phase 0-1. Với hệ thống latency-sensitive, cân nhắc GCLatencyMode.SustainedLowLatency.

Exercise

Chọn 1 endpoint có P99 latency cao bất thường trong hệ thống hiện tại, đo allocation rate của nó bằng dotnet-counters dưới tải, xác nhận có tương quan với GC pause hay không.

Finalizer & IDisposable Pattern

Concept

Finalizer (~ClassName()) là "lưới an toàn" cuối cùng để giải phóng unmanaged resource nếu lập trình viên quên gọi Dispose — nhưng object có finalizer cần ÍT NHẤT 2 lần GC cycle để thực sự bị thu hồi (lần 1: finalize queue, lần 2: thực sự free), và finalizer chạy trên 1 thread riêng có thể bị nghẽn nếu finalizer chậm. Dispose pattern chuẩn giải phóng resource ngay lập tức và gọi GC.SuppressFinalize(this) để bỏ qua finalizer không cần thiết.

Mental Model

Finalizer giống "đội cứu hộ" chỉ tới khi bạn quên khoá vòi nước — họ sẽ tới, nhưng chậm và tốn thêm 1 vòng kiểm tra. Gọi Dispose chủ động giống tự khoá vòi ngay khi xong việc — nhanh, chắc chắn, không cần đội cứu hộ can thiệp.

Ví dụ
public class ResourceHolder : IDisposable {
    private bool _disposed;
    private readonly IntPtr _handle;

    public void Dispose() {
        Dispose(true);
        GC.SuppressFinalize(this); // bỏ qua finalizer vì đã dọn thủ công
    }
    protected virtual void Dispose(bool disposing) {
        if (_disposed) return;
        // giải phóng unmanaged handle ở đây
        _disposed = true;
    }
    ~ResourceHolder() => Dispose(false); // lưới an toàn
}
Experiment

Tạo 100,000 object có finalizer nhưng KHÔNG gọi Dispose, so với 100,000 object gọi Dispose đúng cách. Đo thời gian toàn bộ object thực sự bị thu hồi khỏi heap bằng dotnet-gcdump chụp nhiều lần.

Benchmark

BenchmarkDotNet đo throughput tạo+huỷ object có finalizer vs không có finalizer — object có finalizer luôn chậm hơn đáng kể do phải qua finalization queue.

Profiling

dotnet-counters hoặc dotnet-dump có thể show finalization queue length — queue dài bất thường là dấu hiệu leak resource hoặc finalizer bị block.

Optimization

Luôn implement Dispose pattern đầy đủ cho class quản lý unmanaged resource; luôn gọi SuppressFinalize. Tránh finalizer cho class không thực sự cần (không giữ unmanaged resource).

Exercise

Audit 1 class trong project hiện tại có finalizer, xác nhận nó có gọi SuppressFinalize trong Dispose hay không, sửa nếu thiếu.

GC Tuning

Concept

Ngoài Workstation/Server và Background GC, .NET expose thêm knobs: GCHeapHardLimit (giới hạn cứng tổng heap, quan trọng trong container), GCConserveMemory (đánh đổi throughput lấy memory footprint thấp hơn), DOTNET_gcServer/DOTNET_GCHeapCount (số heap khi Server GC). Tuning GC là công cụ cuối cùng — chỉ nên dùng SAU KHI đã giảm allocation rate ở tầng code.

Mental Model

Tuning GC config giống chỉnh thông số máy điều hoà (công suất, chế độ tiết kiệm) — hữu ích, nhưng không thay thế được việc sửa cách nhiệt của căn nhà (giảm allocation trong code). Sửa cách nhiệt trước, chỉnh điều hoà sau.

Ví dụ
<PropertyGroup>
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
  <GCHeapHardLimit>0x10000000</GCHeapHardLimit> <!-- ~256MB, hex -->

</PropertyGroup>
Experiment

So sánh memory footprint và throughput của cùng ứng dụng với GCConserveMemory = 0 vs = 9 dưới tải ổn định trong 5 phút.

Đo P50/P99 latency và peak memory với các giá trị GCHeapHardLimit khác nhau trong container giới hạn 512MB — tìm điểm cân bằng giữa OOM risk và GC frequency.

Profiling

dotnet-counters theo dõi gc-heap-size so với giới hạn đã set để xác nhận cấu hình đang có tác dụng như dự kiến.

Optimization

Set GCHeapHardLimit phù hợp với container memory limit (thường 75-80% limit) để tránh bị OOM-killed. Chỉ tăng GCConserveMemory khi memory là ràng buộc quan trọng hơn latency.

SHOULD KNOW

CPU Cycle · Instruction Pipeline · Branch Prediction

Concept

CPU hiện đại không chạy 1 instruction xong mới sang instruction tiếp — nó pipeline nhiều instruction ở các giai đoạn khác nhau (fetch/decode/execute) cùng lúc, như dây chuyền lắp ráp. Branch prediction đoán trước nhánh if/else nào sẽ được thực thi để tiếp tục nạp lệnh trước, tránh dây chuyền bị "đứng hình" chờ kết quả so sánh. Đoán sai (branch misprediction) buộc CPU xả sạch pipeline và làm lại — tốn hàng chục cycle.

Mental Model

Pipeline giống dây chuyền sản xuất ô tô: trạm 1 đang lắp khung xe A trong khi trạm 2 đang sơn xe B (khung đã lắp trước đó) — nhiều xe được xử lý song song ở các công đoạn khác nhau. Branch misprediction giống dây chuyền lỡ chuẩn bị sẵn phụ tùng cho "xe màu đỏ" nhưng hoá ra là xe màu xanh — phải bỏ hết phụ tùng đã chuẩn bị sai và lấy lại từ đầu.

Ví dụ
// mảng ĐÃ SORT — CPU dự đoán nhánh chính xác gần như 100%
foreach (var x in sortedArray)
    if (x > threshold) sum += x; // pattern nhánh đều đặn, dễ đoán

// mảng KHÔNG sort — nhánh random, CPU đoán sai liên tục
foreach (var x in shuffledArray)
    if (x > threshold) sum += x;
Experiment

Kinh điển "branch prediction benchmark": tạo array 1 triệu số ngẫu nhiên, chạy vòng lặp if (x > threshold) sum += x trên bản gốc (random) vs bản đã Array.Sort() trước. Đo thời gian — bản sort thường nhanh hơn 2-6 lần dù thuật toán giống hệt.

Benchmark

BenchmarkDotNet với [Arguments] cho 2 biến thể dữ liệu (sorted/unsorted), cùng logic xử lý — cột Mean thể hiện rõ chênh lệch chỉ do branch prediction, không phải thuật toán.

Profiling

Optimization

Trong hot loop với điều kiện lọc, cân nhắc sắp xếp dữ liệu trước nếu có thể, hoặc dùng branchless technique (toán học thay vì if) khi thực sự cần siết tối đa hiệu năng ở phần cực nóng của hệ thống.

Cache Hierarchy (L1/L2/L3) & Cache Line

Concept

CPU truy cập RAM chậm hơn cache hàng chục-hàng trăm lần, nên có nhiều tầng cache nhỏ-nhanh gần lõi: L1 (~1ns, vài chục KB, riêng mỗi core), L2 (~4ns, vài trăm KB-MB, riêng mỗi core), L3 (~15-40ns, vài-vài chục MB, dùng chung). Dữ liệu được nạp theo cache line (thường 64 byte) — truy cập 1 byte kéo theo cả 64 byte lân cận được nạp vào cache, nên truy cập tuần tự (sequential) tận dụng cache tốt hơn nhiều so với truy cập nhảy cóc (random/scattered).

Mental Model

Cache giống ngăn kéo trên bàn (L1), tủ trong phòng (L2), kho tầng dưới (L3), và nhà kho ở xa thành phố (RAM) — càng gần bàn làm việc càng nhanh lấy nhưng càng nhỏ. Đọc dữ liệu liên tục (array) giống lấy cả 1 chồng hồ sơ liền kề trong ngăn kéo cùng lúc; nhảy lung tung giữa các linked list node rải rác khắp bộ nhớ giống mỗi lần phải chạy ra tận kho xa lấy 1 tờ giấy.

Ví dụ
// truy cập TUẦN TỰ — cache-friendly
int sum = 0;
for (int i = 0; i < arr.Length; i++) sum += arr[i];

// truy cập theo LINKED LIST — mỗi node có thể nằm rải rác trên heap, cache-unfriendly
var node = list.First;
while (node != null) { sum += node.Value; node = node.Next; }
Experiment

Tổng hợp 10 triệu số qua int[] (array, tuần tự) vs LinkedList<int> (mỗi node là object riêng biệt trên heap) — đo thời gian, dù cùng độ phức tạp O(n), array thường nhanh hơn 5-10 lần vì cache locality.

Benchmark

BenchmarkDotNet so sánh duyệt array 2 chiều theo row-major (đúng thứ tự bộ nhớ, C# lưu array 2D theo row-major) vs column-major (nhảy cóc) — chênh lệch rõ rệt dù số phép toán y hệt.

Profiling

perf stat (Linux) với counter cache-misses so sánh trực tiếp giữa 2 kiểu truy cập — con số cache-miss cao tương ứng với thời gian chạy chậm hơn, chứng minh nhân quả.

Optimization

Ưu tiên cấu trúc dữ liệu liên tục (array, List<T>, Span<T>) cho hot path thay vì linked structure khi có thể. Duyệt array đa chiều đúng thứ tự lưu trữ trong bộ nhớ (row-major trong C#).

Exercise

Viết hàm nhân ma trận 2 cách: đúng thứ tự cache-friendly và sai thứ tự, đo chênh lệch trên ma trận 1000x1000, giải thích bằng cache line và cache-miss.

SIMD · Multicore · Context Switching

Concept

SIMD (Single Instruction Multiple Data) cho phép 1 instruction CPU xử lý nhiều giá trị cùng lúc (ví dụ 8 số float trong 1 lệnh AVX). Multicore cho phép chạy song song thật (parallel), khác với concurrency (xen kẽ trên 1 core). Context switching là chi phí CPU phải lưu/khôi phục trạng thái khi chuyển giữa các thread — quá nhiều thread hơn số core thực tế gây context switching thừa, giảm hiệu năng thay vì tăng.

Mental Model

SIMD giống 1 công nhân có thể đóng 8 cái đinh cùng lúc bằng 1 cú búa đặc biệt thay vì đóng từng cái. Multicore giống thuê thêm công nhân làm song song thật sự. Context switch giống công nhân phải dừng việc đang làm, cất dụng cụ, rồi lấy dụng cụ khác ra làm việc mới — tốn thời gian "chuyển cảnh" nếu đổi việc quá thường xuyên.

Ví dụ
using System.Numerics;
Vector<float> va = new(arrayA, 0);
Vector<float> vb = new(arrayB, 0);
Vector<float> result = va + vb; // cộng nhiều float cùng 1 lệnh CPU
Experiment

Cộng 2 array 10 triệu phần tử float: vòng lặp thường vs dùng System.Numerics.Vector<float>. Đo thời gian — SIMD thường nhanh hơn 4-8 lần tuỳ độ rộng vector của CPU.

Benchmark

BenchmarkDotNet so sánh xử lý tuần tự vs Parallel.For trên 8 core cho workload CPU-bound thuần tuý — quan sát throughput tăng gần tuyến tính theo số core tới một điểm bão hoà.

Profiling

dotnet-counters counter threadpool-thread-count và CPU usage per-core (qua OS tool) để xác nhận công việc thực sự phân bổ đều trên các core khi dùng Parallel.For.

Optimization

Dùng SIMD cho workload toán học lặp lại trên mảng lớn (xử lý ảnh, tín hiệu). Giới hạn số thread song song gần với số core thực tế (ThreadPool đã tự làm điều này ở mức tốt cho hầu hết trường hợp) để tránh context-switch overhead.

Exercise

Viết hàm tính tổng bình phương khoảng cách giữa 2 tập điểm 3D bằng vòng lặp thường và bằng Vector<float>, benchmark trên tập 5 triệu điểm.

RAM · Virtual Memory · Paging

Concept

Mỗi process (bao gồm .NET process) chạy trong không gian địa chỉ ảo (virtual memory) riêng, được OS ánh xạ (map) sang RAM vật lý theo từng trang (page, thường 4KB). Khi ứng dụng dùng nhiều memory hơn RAM vật lý sẵn có, OS phải "swap"/page dữ liệu ra đĩa — chậm hơn RAM hàng nghìn lần. Working set là tập hợp trang thực sự đang active trong RAM của process.

Mental Model

Virtual memory giống mỗi công ty (process) có 1 hệ thống đánh số phòng riêng biệt (địa chỉ ảo) dù toà nhà thật (RAM) dùng chung cho nhiều công ty — bảo vệ công ty này không đọc được phòng của công ty khác. Paging ra đĩa giống khi phòng làm việc chật, phải chuyển bớt hồ sơ ít dùng xuống kho ở tầng hầm xa (đĩa) — lấy lại chậm hơn nhiều.

Ví dụ
// quan sát working set của process .NET hiện tại
var proc = Process.GetCurrentProcess();
Console.WriteLine(proc.WorkingSet64);
Experiment

Chạy ứng dụng cấp phát dần tới khi memory usage vượt RAM vật lý khả dụng trên máy test (cẩn thận, dùng máy ảo/container giới hạn), quan sát latency tăng đột biến khi OS bắt đầu page ra đĩa.

Benchmark

Không benchmark trực tiếp bằng BenchmarkDotNet (nó không mô phỏng memory pressure hệ thống tốt) — dùng load test kết hợp giới hạn container memory để quan sát hành vi thật.

Profiling

dotnet-counters counter working-set so với memory limit của container; trên Linux, vmstat cho thấy hoạt động swap (si/so column) khi hệ thống bắt đầu page.

Optimization

Set memory limit container thấp hơn RAM host một khoảng an toàn, đặt GCHeapHardLimit phù hợp (đã học ở Phase 3) để tránh chạm ngưỡng OOM-kill hoặc swap.

Exercise

Kiểm tra working set hiện tại của 1 service .NET đang chạy so với memory limit được cấp phát, đánh giá có đang gần ngưỡng nguy hiểm hay không.

Case Study: Cùng Big-O, Khác Performance Thực Tế

Concept

Big-O đo số phép toán theo kích thước input, KHÔNG đo chi phí thực tế mỗi phép toán trên phần cứng — 2 đoạn code O(n) có thể chênh lệch 10 lần tốc độ vì: cache locality khác nhau, allocation rate khác nhau (GC pressure), branch prediction khác nhau, hoặc 1 bên tận dụng SIMD còn bên kia không. Đây là lý do "phân tích thuật toán" chỉ là bước đầu, "đo trên phần cứng thật" mới là sự thật cuối cùng.

Mental Model

Big-O giống việc so sánh 2 công thức nấu ăn chỉ dựa trên số bước — không tính tới việc 1 công thức dùng nguyên liệu để sẵn trong bếp (cache-friendly) còn công thức kia phải chạy ra chợ xa mỗi bước (cache-unfriendly, allocation nặng).

Ví dụ
// cả 2 đều O(n) nhưng tốc độ thực tế khác xa nhau
int Sum1(int[] arr) { int s=0; foreach(var x in arr) s+=x; return s; }
int Sum2(List<int> boxedViaObj) { // giả sử List<object> chứa int đã box
    int s=0; foreach(object o in boxedViaObj) s += (int)o; return s; // mỗi phần tử nằm rải rác trên heap
}
Experiment

Thu thập lại toàn bộ số liệu từ các experiment trước trong roadmap này (struct vs class, sorted vs unsorted, array vs linked list) và tổng hợp thành 1 bảng "cùng Big-O — chênh lệch thực tế bao nhiêu lần" — đây chính là bằng chứng thực nghiệm cho case study này.

Benchmark

Không có benchmark mới — đây là bài tổng hợp, dùng lại toàn bộ kết quả BenchmarkDotNet đã thu thập từ Phase 0-4.

Profiling

Tổng hợp lại các phát hiện từ perf stat (cache-misses, branch-misses) và dotnet-counters (allocation rate, GC count) thành 1 báo cáo "vì sao chậm" đầy đủ bằng chứng cho từng case.

Optimization

Luôn đo trên phần cứng thật trước khi kết luận thuật toán nào "nhanh hơn" chỉ dựa trên Big-O. Big-O tốt để loại bỏ thuật toán tệ rõ ràng (O(n²) vs O(n log n) trên n lớn), nhưng không đủ để chọn giữa các cài đặt cùng độ phức tạp.

MUST KNOW

Process · Thread · ThreadPool

Concept

Process là 1 không gian địa chỉ độc lập với resource riêng (memory, handle). Thread là đơn vị thực thi bên trong process, chia sẻ memory với các thread khác cùng process — tạo thread tốn kém (stack riêng ~1MB mặc định, kernel object). ThreadPool là 1 tập thread được quản lý sẵn, tái sử dụng cho các Task ngắn hạn, tránh chi phí tạo/huỷ thread liên tục; nó tự động scale số worker thread theo tải (dần dần, không ngay lập tức).

Mental Model

Process giống 1 căn nhà riêng biệt hoàn toàn. Thread giống người trong nhà đó, dùng chung bếp/phòng khách (memory) nhưng mỗi người có phòng riêng nhỏ (stack). ThreadPool giống 1 đội nhân viên trực sẵn tại chỗ thay vì mỗi lần có việc lại phải tuyển người mới (tạo thread mới) rồi sa thải ngay sau khi xong (huỷ thread) — tuyển/sa thải liên tục rất tốn kém.

Ví dụ
ThreadPool.QueueUserWorkItem(_ => DoWork());
// hoặc qua Task, cách hiện đại được khuyến khích:
Task.Run(() => DoWork());
Experiment

So sánh tạo 10,000 new Thread() thủ công và chạy công việc nhỏ, với 10,000 Task.Run dùng ThreadPool — đo tổng thời gian và memory footprint (mỗi Thread tốn ~1MB stack, 10,000 thread = ~10GB nếu tạo hết cùng lúc, thường sẽ fail).

Benchmark

BenchmarkDotNet đo overhead tạo+chạy+huỷ 1 Thread vs enqueue 1 Task vào ThreadPool đã warm — chênh lệch có thể tới hàng trăm lần cho công việc rất ngắn.

Profiling

dotnet-counters counter threadpool-thread-count và threadpool-queue-length để xem ThreadPool scale ra sao dưới tải tăng dần — nó KHÔNG tạo thread mới ngay lập tức, có độ trễ "warm-up" (thuật toán hill-climbing).

Optimization

Luôn dùng ThreadPool (qua Task.Run) cho công việc CPU-bound ngắn hạn thay vì tự tạo Thread. Chỉ tạo Thread thủ công khi cần kiểm soát đặc biệt (background thread dài hạn, priority riêng, apartment state cho COM interop).

Exercise

Đo thời gian ThreadPool "warm up" tới khi đạt đủ thread để xử lý 1 spike 1000 request đồng thời từ trạng thái idle — quan sát độ trễ ban đầu này trong dotnet-counters.

MUST KNOW

Race Condition · Deadlock · Lock Contention

Concept

Race condition xảy ra khi kết quả phụ thuộc vào thứ tự thực thi không xác định giữa nhiều thread truy cập shared state không đồng bộ hoá. Deadlock xảy ra khi 2+ thread chờ nhau giữ lock của nhau theo chu trình khép kín (circular wait), không bao giờ tiến triển. Lock contention là khi nhiều thread liên tục tranh chấp cùng 1 lock, khiến phần lớn thời gian bị dành cho chờ đợi thay vì làm việc thực sự — throughput giảm dù CPU vẫn "bận" (busy nhưng không hữu ích).

Mental Model

Race condition giống 2 người cùng ghi vào 1 tờ giấy cùng lúc không hẹn trước — kết quả cuối cùng tuỳ ai ghi sau đè lên ai. Deadlock giống 2 người đứng ở 2 đầu hành lang hẹp, mỗi người chờ người kia nhường đường trước — cả 2 đứng mãi. Lock contention giống 1 cửa hẹp mà cả trăm người cùng chen vào — hầu hết thời gian là đứng chờ, không phải đi qua.

Ví dụ
// DEADLOCK kinh điển: thứ tự lock ngược nhau giữa 2 thread
// Thread A: lock(obj1) { lock(obj2) { ... } }
// Thread B: lock(obj2) { lock(obj1) { ... } }  ← ngược thứ tự → deadlock có thể xảy ra

// RACE CONDITION: tăng biến không đồng bộ
private int _count;
void Increment() => _count++; // KHÔNG atomic — đọc, cộng, ghi là 3 bước riêng
Experiment

Cho 8 thread cùng gọi Increment() (bản race condition) 1 triệu lần mỗi thread, in kết quả cuối — thường KHÁC 8,000,000 (bằng chứng race condition sống). Sửa bằng lock hoặc Interlocked, chạy lại, kết quả luôn đúng.

Benchmark

Tạo deadlock có chủ đích (2 lock ngược thứ tự giữa 2 task) trong môi trường test, dùng timeout để phát hiện thay vì để treo mãi — đo được rằng deadlock KHÔNG xảy ra 100% số lần chạy (do timing), đây là lý do nó khó debug trong production.

Profiling

dotnet-dump analyze trên process bị treo nghi deadlock: dùng lệnh syncblk để liệt kê tất cả lock đang giữ và thread nào đang chờ gì — xác định chính xác chu trình circular wait.

Optimization

Luôn lock theo 1 thứ tự cố định toàn hệ thống để loại bỏ khả năng deadlock circular wait. Giữ critical section (thời gian giữ lock) càng ngắn càng tốt để giảm contention. Cân nhắc lock-free (Interlocked) cho hot path đơn giản.

Exercise

Viết 1 đoạn code deadlock có chủ đích với 2 lock, dùng dotnet-dump để phân tích và xác định chính xác cặp thread + lock gây deadlock từ dump file.

ThreadPool Starvation — Nguyên Nhân & Cách Detect

Concept

ThreadPool starvation xảy ra khi tất cả worker thread đang bận (thường bị BLOCK bởi công việc đồng bộ chạy lâu, ví dụ gọi .Result/.Wait() trên Task, hoặc I/O đồng bộ), trong khi công việc mới liên tục được enqueue và phải xếp hàng chờ. ThreadPool chỉ tạo thêm thread mới rất chậm (thuật toán hill-climbing, mặc định ~1-2 thread/giây sau khi vượt ngưỡng MinThreads) — dẫn tới latency tăng vọt dù CPU không hề bận.

Mental Model

Giống 1 quầy phục vụ có 10 nhân viên (thread), nhưng vì lý do nào đó mỗi nhân viên đang phải "đứng chờ điện thoại" (blocking call) thay vì phục vụ khách tiếp theo. Khách mới xếp hàng dài ra (queue length tăng), quản lý (ThreadPool) chỉ tuyển thêm nhân viên mới rất từ từ — khách chờ rất lâu dù cửa hàng "trông" không hề đông đúc nếu chỉ nhìn số nhân viên.

Ví dụ
// NGUYÊN NHÂN KINH ĐIỂN gây starvation trong ASP.NET Core:
[HttpGet]
public string Get() {
    var result = _httpClient.GetStringAsync(url).Result; // BLOCK 1 worker thread!
    return result;
}
// SỬA: dùng async xuyên suốt
[HttpGet]
public async Task<string> Get() =>
    await _httpClient.GetStringAsync(url);
Experiment

Xây 1 API endpoint cố tình gọi .Result trên 1 Task I/O-bound giả lập (delay 500ms). Load test với 200 request đồng thời — quan sát P99 latency tăng phi tuyến (không phải 500ms mà có thể lên tới hàng chục giây) do request phải xếp hàng chờ thread rảnh.

Benchmark

So sánh cùng load test trên bản blocking (.Result) vs bản async đúng cách (await) — throughput (req/s) của bản async thường cao hơn hàng chục lần dưới tải đồng thời lớn.

Profiling

dotnet-counters monitor --counters System.Runtime[threadpool-queue-length,threadpool-thread-count] — dấu hiệu starvation rõ ràng: queue-length tăng liên tục trong khi thread-count tăng rất chậm, CPU usage thấp dù latency cao.

Optimization

Không bao giờ gọi .Result/.Wait()/.GetAwaiter().GetResult() trên Task trong request path. Nếu bắt buộc phải tăng MinThreads tạm thời (ThreadPool.SetMinThreads) như biện pháp chữa cháy, coi đó là dấu hiệu cần tìm gốc rễ blocking call, không phải giải pháp lâu dài.

Exercise

Tìm và liệt kê mọi chỗ dùng .Result/.Wait() trong project hiện tại (grep code), đánh giá từng chỗ có nguy cơ gây starvation dưới tải cao hay không.

MUST KNOW

Task · Task Scheduler · Async State Machine

Concept

Compiler biến method async thành 1 struct/class ẩn implement IAsyncStateMachine — mỗi điểm await là 1 "state" trong máy trạng thái đó. Khi gặp await trên 1 operation chưa hoàn thành, method thực sự RETURN NGAY (trả Task chưa complete) về caller, giải phóng thread hiện tại — không hề "chờ" (block) gì cả. Khi operation xong, continuation (phần code sau await) được lên lịch chạy tiếp, có thể trên thread khác.

Mental Model

Đây là lý do async/await ≠ tạo thread mới: nó giống 1 người phục vụ nhà hàng ghi order rồi đi phục vụ bàn khác ngay (giải phóng thread), thay vì đứng yên tại bếp chờ món ăn xong (blocking). Khi bếp báo món xong (callback/continuation), MỘT người phục vụ nào đó rảnh (có thể là người khác) sẽ mang món ra — không nhất thiết là người ghi order ban đầu.

Ví dụ
// gần đúng những gì compiler sinh ra (rút gọn khái niệm):
async Task<int> Method() {
    var x = await SomethingAsync(); // state 0 → state 1
    return x + 1;
}
// compiler sinh: struct StateMachine { int state; TaskAwaiter awaiter; ...
//   MoveNext() { switch(state) { case 0: ...; case 1: ...; } } }
Experiment

Gọi 1 async method có 3 điểm await liên tiếp từ 1 thread cụ thể, in Thread.CurrentThread.ManagedThreadId trước và sau mỗi await — trong ASP.NET Core (không có SynchronizationContext), thread ID có thể khác nhau giữa các đoạn, chứng minh continuation không nhất thiết chạy lại trên thread gốc.

Benchmark

BenchmarkDotNet đo overhead của async state machine cho method hoàn toàn đồng bộ bên trong (không có I/O thật) so với method đồng bộ thuần — có overhead nhỏ nhưng đo được từ việc tạo state machine object.

Profiling

dotnet-trace với TplEventSource provider bắt được các event Task creation/completion/continuation-scheduling — dùng để trace chính xác luồng thực thi bất đồng bộ phức tạp trong production.

Optimization

Hiểu rằng await không tốn "1 thread cho mỗi request đang chờ I/O" là chìa khoá để thiết kế hệ thống I/O-bound chịu tải cao (hàng chục nghìn connection đồng thời) mà không cần hàng chục nghìn thread.

SHOULD KNOW

SynchronizationContext · Continuation · Deadlock Kinh Điển

Concept

SynchronizationContext quyết định continuation sau await chạy ở đâu — UI framework (WPF/WinForms) có context đảm bảo continuation quay lại đúng UI thread. ASP.NET Core (từ Core trở đi) KHÔNG có SynchronizationContext mặc định, nên continuation có thể chạy trên bất kỳ ThreadPool thread nào. Trong môi trường CÓ SynchronizationContext (như WPF/ASP.NET Framework cũ), gọi .Result/.Wait() từ UI/request thread trên 1 Task đang chờ continuation quay lại chính context đó gây deadlock kinh điển: thread bị block chờ Task, Task chờ context rảnh để chạy continuation, context bị chiếm bởi thread đang block — chờ nhau vô tận.

Mental Model

Giống 1 nhân viên lễ tân (UI thread) tự tay đi giao 1 gói hàng (blocking call), trong khi gói hàng đó chỉ có thể được xác nhận nhận thành công (continuation) bởi CHÍNH nhân viên lễ tân đó quay lại bàn — nhưng anh ta đang mắc kẹt trên đường đi giao hàng. Cả 2 phía chờ nhau mãi mãi.

Ví dụ
// deadlock kinh điển trong môi trường CÓ SynchronizationContext
public void Button_Click(object sender, EventArgs e) {
    var result = LoadDataAsync().Result; // DEADLOCK trên UI thread
}
// SỬA: dùng async xuyên suốt, hoặc ConfigureAwait(false) trong thư viện
private async void Button_Click(object sender, EventArgs e) {
    var result = await LoadDataAsync();
}
Experiment

Mô phỏng lại deadlock này trong 1 ứng dụng WPF/Console có custom SynchronizationContext đơn giản — quan sát treo thực sự, rồi sửa bằng async xuyên suốt để thấy hết treo.

Benchmark

Không áp dụng — đây là bug về correctness (deadlock), không phải vấn đề tốc độ.

Profiling

dotnet-dump analyze trên process treo: lệnh clrstack trên từng thread cho thấy 1 thread đang ở Task.Wait, thread khác (hoặc chính context) đang chờ được cấp quyền chạy continuation — bằng chứng trực quan cho deadlock loại này.

Optimization

Viết thư viện dùng lại nhiều nơi (không biết trước context caller) nên dùng ConfigureAwait(false) để continuation không cố quay lại context gốc, giảm rủi ro deadlock và cải thiện nhẹ hiệu năng (bỏ qua bước capture/marshal context).

Exercise

SHOULD KNOW

I/O-bound vs CPU-bound · ValueTask · ConfigureAwait

Concept

I/O-bound (gọi DB, HTTP, đọc file) nên dùng async/await tự nhiên — không tốn thread trong lúc chờ. CPU-bound (tính toán nặng) không có gì để "await" thực sự chờ — cần Task.Run để đẩy công việc sang ThreadPool thread khác nếu muốn không block thread gọi (ví dụ UI thread), nhưng bản thân công việc vẫn CHIẾM 1 thread trong suốt thời gian tính toán, khác hoàn toàn với I/O-bound.

Mental Model

I/O-bound giống đặt đồ ăn rồi đi làm việc khác trong lúc chờ (không chiếm nhân viên). CPU-bound giống tự tay bạn phải ngồi tính một phép toán phức tạp — dù giao việc cho ai đó (Task.Run), người đó vẫn phải ngồi tính liên tục, không "rảnh tay" làm việc khác trong lúc tính.

Ví dụ
// SAI: dùng Task.Run cho I/O-bound — lãng phí 1 thread không cần thiết
await Task.Run(() => httpClient.GetStringAsync(url).Result);

// ĐÚNG: I/O-bound await trực tiếp
await httpClient.GetStringAsync(url);

// ĐÚNG: CPU-bound đẩy sang ThreadPool nếu cần giải phóng caller thread
await Task.Run(() => HeavyComputation());
Experiment

So sánh 100 request gọi trực tiếp await httpClient.GetStringAsync vs bọc trong Task.Run không cần thiết — theo dõi threadpool-thread-count, bản Task.Run tốn nhiều thread hơn hẳn cho cùng khối lượng công việc I/O.

Benchmark

BenchmarkDotNet đo overhead ConfigureAwait(false) vs không dùng trong 1 chuỗi 10 await liên tiếp trong thư viện không cần context — chênh lệch nhỏ nhưng đo được, cộng dồn có ý nghĩa ở hot path.

Profiling

dotnet-counters threadpool-thread-count là chỉ số trực tiếp để phát hiện lỗi dùng Task.Run sai chỗ cho I/O-bound trong code review thực tế.

Optimization

Không bao giờ bọc I/O-bound API trong Task.Run. Dùng Task.Run đúng mục đích: đẩy CPU-bound work ra khỏi thread cần giữ rảnh (UI thread, hoặc để không chặn 1 request handler đang cần trả lời nhanh các phần khác).

Exercise

Audit code hiện tại tìm chỗ nào bọc Task.Run quanh 1 call I/O-bound đã có sẵn bản Async — đây là anti-pattern phổ biến cần sửa.

Kestrel · Middleware Pipeline · HTTP Request Lifecycle

Concept

Kestrel là web server nội bộ của ASP.NET Core, xử lý raw socket → HTTP parsing → đẩy request vào middleware pipeline. Mỗi middleware là 1 mắt xích trong chuỗi, có thể xử lý trước/sau khi gọi middleware tiếp theo (dạng nested delegate). Thứ tự đăng ký middleware quyết định thứ tự thực thi — middleware đặt sai vị trí (ví dụ auth sau khi đã xử lý business logic) là lỗi kiến trúc lẫn hiệu năng.

Mental Model

Middleware pipeline giống dây chuyền kiểm tra an ninh sân bay — mỗi trạm (middleware) có thể chặn bạn lại hoặc cho qua rồi trạm sau tiếp tục xử lý, và có thể làm thêm việc khi bạn quay lại (response đi ngược pipeline). Thứ tự trạm sai (kiểm tra vé sau khi đã lên máy bay) gây lãng phí tài nguyên xử lý những request lẽ ra nên bị chặn sớm.

Ví dụ
app.UseExceptionHandler("/error"); // nên ở đầu — bắt lỗi toàn bộ pipeline sau nó
app.UseHttpsRedirection();
app.UseAuthentication();       // xác thực TRƯỚC khi vào business logic
app.UseAuthorization();
app.MapControllers();          // business logic ở cuối
Experiment

Đo overhead thời gian của từng middleware bằng cách tự viết 1 middleware ghi Stopwatch timestamp trước/sau _next(context) ở vị trí khác nhau trong pipeline, xác định middleware nào chiếm nhiều thời gian nhất trên request thật.

Benchmark

Dùng công cụ load test (ví dụ bombardier/k6) đo baseline throughput của pipeline tối giản (chỉ 1 middleware trả "OK") vs pipeline đầy đủ của ứng dụng thật — chênh lệch cho biết tổng overhead framework.

Profiling

dotnet-trace với ASP.NET Core provider ghi lại chính xác thời gian mỗi middleware + request handler, xem trực quan qua Speedscope hoặc PerfView.

Optimization

Đặt middleware "chặn sớm" (auth, rate limiting) trước middleware tốn tài nguyên. Loại bỏ middleware không cần thiết trên hot path (ví dụ logging quá chi tiết trên mọi request).

JSON Serialization & Request Allocation

Concept

Mỗi request/response JSON đi qua serialize/deserialize — System.Text.Json (mặc định, dùng Utf8JsonReader/Utf8JsonWriter dựa trên Span) nhanh và ít allocation hơn Newtonsoft.Json cũ trong hầu hết trường hợp. Mental Model

Serialize giống dịch tài liệu từ "ngôn ngữ nội bộ" (object C#) sang "ngôn ngữ giao tiếp chung" (JSON text) — dịch giả càng phải xử lý nhiều chi tiết thừa (field không cần), càng tốn thời gian và giấy (băng thông).

// DTO gọn, chỉ chứa field client thực sự cần
public record ProductListItemDto(int Id, string Name, decimal Price);
// tránh trả thẳng entity EF Core đầy đủ navigation property ra API

Luôn dùng DTO/projection gọn cho response, không trả thẳng entity. Cân nhắc System.Text.Json source generator (JsonSerializerContext) để loại bỏ reflection lúc runtime, đặc biệt quan trọng với Native AOT.

MUST KNOW

Connection Pooling & HttpClient

Concept

Tạo new HttpClient() mỗi request là anti-pattern nổi tiếng: dù HttpClient implement IDisposable, socket bên dưới không được giải phóng ngay (TIME_WAIT state), dẫn tới socket exhaustion dưới tải cao. Dùng IHttpClientFactory (đăng ký qua DI) quản lý pool HttpMessageHandler bên dưới, tái sử dụng connection đúng cách đồng thời vẫn xử lý DNS refresh định kỳ.

Mental Model

Giống việc mỗi lần gọi điện lại phải lắp 1 đường dây điện thoại mới rồi cắt bỏ ngay sau cuộc gọi — tốn kém và dần hết dây (socket) khả dụng. IHttpClientFactory giống 1 tổng đài dùng chung nhiều đường dây đã sẵn sàng, tái sử dụng cho các cuộc gọi tiếp theo.

Ví dụ
// Program.cs — ĐÚNG
builder.Services.AddHttpClient<MyApiClient>(client => {
    client.BaseAddress = new("https://api.example.com");
});

// SAI: new HttpClient() trong mỗi request handler
Experiment

Load test 1 endpoint gọi ra ngoài 500 request/giây: bản new HttpClient() mỗi request vs bản dùng IHttpClientFactory. Quan sát số lượng socket ở trạng thái TIME_WAIT bằng netstat/ss tăng dần ở bản đầu.

Benchmark

Đo thời gian phản hồi P99 của 2 bản dưới tải kéo dài 5 phút — bản new HttpClient() thường suy giảm hiệu năng dần theo thời gian do socket exhaustion.

Profiling

dotnet-counters không có counter socket trực tiếp — kết hợp OS-level tool (netstat -an | grep TIME_WAIT | wc -l) với thời điểm bắt đầu giảm hiệu năng để chứng minh nhân quả.

Optimization

Luôn dùng IHttpClientFactory (typed client hoặc named client) đăng ký qua DI. Với call ra service downstream, cân nhắc thêm Polly cho retry/circuit breaker tích hợp sẵn qua AddHttpClient.

Exercise

MUST KNOW

EF Core Performance — Tracking · N+1 · Index

Concept

EF Core mặc định "track" mọi entity trả về (change tracking để phục vụ Update sau này) — tốn CPU + memory nếu bạn chỉ đọc dữ liệu (read-only query nên dùng AsNoTracking()). N+1 query là lỗi kinh điển: query danh sách cha (1 query), rồi lặp qua từng cha để lazy-load con (N query riêng) thay vì 1 query duy nhất có Include/join. Index sai hoặc thiếu khiến query full table scan thay vì seek trực tiếp — khác biệt O(n) vs O(log n) trên bảng lớn.

Mental Model

Change tracking giống việc chụp ảnh "trước" mọi món đồ bạn cầm lên chỉ để lỡ sau này bạn có sửa gì thì so sánh được — nếu bạn chỉ xem rồi đặt lại y nguyên (read-only), việc chụp ảnh đó hoàn toàn lãng phí. N+1 giống việc hỏi "con của người này là ai" riêng biệt cho từng người trong danh sách 100 người, thay vì hỏi 1 câu "cho tôi biết con của tất cả 100 người này".

Ví dụ
// N+1 — lazy loading trong vòng lặp (BAD)
var orders = db.Orders.ToList();
foreach (var o in orders)
    Console.WriteLine(o.Customer.Name); // mỗi dòng = 1 query riêng!

// SỬA: Include + AsNoTracking cho read-only
var orders = db.Orders
    .Include(o => o.Customer)
    .AsNoTracking()
    .ToList(); // 1 query duy nhất (JOIN), không track
Experiment

Bật db.Database.Log hoặc EF Core logging provider, chạy đoạn code N+1 phía trên với 100 order, đếm số câu SQL thực sự được gửi xuống DB — sẽ thấy 101 query thay vì 1.

Benchmark

Đo thời gian response của endpoint list 100 order: bản N+1, bản Include không AsNoTracking, bản Include + AsNoTracking — thường chênh lệch hàng chục tới hàng trăm lần giữa bản đầu và bản cuối.

Profiling

Dùng SQL Server Profiler / EXPLAIN ANALYZE (PostgreSQL) để xem query có dùng đúng Index hay bị Seq Scan; kết hợp EF Core's ToQueryString() để xem chính xác SQL sinh ra trước khi chạy.

Optimization

Luôn AsNoTracking() cho query read-only. Luôn Include/projection thay vì lazy-load trong vòng lặp. Đánh Index đúng cột dùng trong WHERE/JOIN/ORDER BY thường xuyên — nhưng cân nhắc trade-off Index làm chậm INSERT/UPDATE.

Exercise

Chọn 1 endpoint list trong Techio/TodoList project, bật EF Core query logging, xác nhận không có N+1, kiểm tra query plan bằng EXPLAIN ANALYZE để xác nhận Index đang được dùng.

Caching & Redis

Concept

In-memory cache (IMemoryCache) nhanh nhất nhưng chỉ sống trong 1 instance — không đồng bộ giữa nhiều server (scale-out). Redis (distributed cache) đồng bộ giữa mọi instance, đánh đổi lấy 1 network round-trip mỗi lần truy cập. Cache invalidation (biết khi nào dữ liệu cache đã cũ, cần xoá/refresh) là phần khó nhất — cache sai policy gây bug "dữ liệu cũ" khó phát hiện hơn cả việc không cache.

Mental Model

In-memory cache giống ghi chú dán trên bàn làm việc riêng bạn — nhanh nhưng đồng nghiệp khác không thấy được. Redis giống 1 bảng thông báo chung cả văn phòng nhìn thấy, nhưng phải đi ra bảng đó để đọc (network trip) thay vì nhìn ngay trên bàn.

Ví dụ
var cached = await cache.GetStringAsync(key);
if (cached is null) {
    var data = await _repo.GetExpensiveDataAsync();
    await cache.SetStringAsync(key, JsonSerializer.Serialize(data),
        new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5) });
    return data;
}
return JsonSerializer.Deserialize<T>(cached);
Experiment

Đo P99 latency của 1 endpoint truy vấn DB phức tạp không cache, với cache Redis (5 phút TTL), với cache in-memory — so sánh trade-off latency vs độ tươi (freshness) dữ liệu.

Benchmark

Load test endpoint có cache-hit rate 90% vs 10% (thay đổi key ngẫu nhiên) để thấy lợi ích cache tỉ lệ thuận với cache-hit rate thực tế trong production.

Profiling

Redis có lệnh MONITOR/SLOWLOG để xem command nào chậm; kết hợp dotnet-trace đo network round-trip time thực tế từ app tới Redis.

Optimization

Cache dữ liệu đọc nhiều, ghi ít, chấp nhận được độ trễ nhất định (eventual consistency). Đặt TTL hợp lý theo tần suất thay đổi dữ liệu thực tế, không cache "mù quáng" mọi thứ.

Exercise

Chọn 1 endpoint đọc nhiều, ít thay đổi trong Techio project, thêm cache Redis với TTL phù hợp, đo P99 latency trước/sau dưới load test.

SHOULD KNOW

Rate Limiting

Concept

Rate limiting giới hạn số request/thời gian từ 1 client, bảo vệ hệ thống khỏi bị quá tải (vô tình hoặc cố ý — DoS). ASP.NET Core có Microsoft.AspNetCore.RateLimiting middleware built-in với nhiều thuật toán: Fixed Window, Sliding Window, Token Bucket, Concurrency Limiter — mỗi loại phù hợp pattern traffic khác nhau.

Mental Model

Token Bucket giống 1 xô chứa token được đổ đầy dần theo thời gian — mỗi request tiêu 1 token, xô cạn thì phải chờ. Cho phép burst ngắn hạn (dùng hết token tích luỹ) nhưng vẫn giới hạn tốc độ trung bình dài hạn.

Ví dụ
builder.Services.AddRateLimiter(options => {
    options.AddTokenBucketLimiter("api", opt => {
        opt.TokenLimit = 100;
        opt.TokensPerPeriod = 20;
        opt.ReplenishmentPeriod = TimeSpan.FromSeconds(1);
    });
});
app.UseRateLimiter();
Experiment

Load test 1 endpoint có rate limiting với traffic vượt ngưỡng — quan sát response 429 Too Many Requests xuất hiện đúng theo cấu hình, đo latency của các request được chấp nhận không bị ảnh hưởng bởi các request bị từ chối.

Benchmark

Đo overhead CPU của rate limiting middleware trên request path bình thường (không vượt ngưỡng) — chi phí nên gần như không đáng kể so với business logic.

Profiling

dotnet-counters custom metrics (qua EventCounter tự định nghĩa) để theo dõi tỷ lệ request bị reject theo thời gian thực trong production.

Optimization

Chọn thuật toán rate limit phù hợp traffic pattern: Token Bucket cho phép burst hợp lý, Fixed Window đơn giản nhưng có vấn đề "biên cửa sổ" (2x traffic ở ranh giới 2 window).

Exercise

BenchmarkDotNet Methodology — Warmup, Iteration, Pilot

Concept

BenchmarkDotNet chạy qua nhiều giai đoạn tự động: Pilot (ước lượng số lần lặp cần thiết để đo chính xác), Warmup (chạy vài vòng để JIT warm-up, loại bỏ Tier 0 compilation time khỏi kết quả), rồi mới tới Actual measurement (nhiều iteration để tính thống kê). Đo tay bằng Stopwatch một lần chạy KHÔNG loại trừ được JIT warm-up, GC pause ngẫu nhiên, và biến động hệ thống — dễ cho kết luận sai.

Mental Model

Đo bằng Stopwatch 1 lần giống bấm giờ 1 lần chạy marathon của 1 vận động viên rồi kết luận "đây là tốc độ của họ" — có thể hôm đó họ vừa khởi động chưa xong (JIT warmup) hoặc bị vấp (GC pause ngẫu nhiên). BenchmarkDotNet giống việc cho vận động viên chạy nhiều lần, bỏ qua lần đầu (warmup), rồi lấy trung vị của nhiều lần chạy ổn định.

Ví dụ
[MemoryDiagnoser]
public class StringBenchmark {
    [Benchmark(Baseline = true)]
    public string Concat() { string s=""; for(int i=0;i<1000;i++) s+=i; return s; }

    [Benchmark]
    public string Builder() { var sb=new StringBuilder(); for(int i=0;i<1000;i++) sb.Append(i); return sb.ToString(); }
}
// chạy: BenchmarkRunner.Run<StringBenchmark>();
Experiment

Benchmark

(Đây chính là bài học về benchmark — tự benchmark cả 2 phương pháp đo để có bằng chứng thực nghiệm về độ tin cậy.)

Profiling

Optimization

Đọc Thống Kê: Mean · Median · Percentile · Statistical Noise

Concept

Mean (trung bình) bị kéo lệch mạnh bởi outlier (1 lần đo bị GC pause đúng lúc). Median (trung vị) bền vững hơn với outlier — thường phản ánh "trải nghiệm điển hình" tốt hơn. Percentile (P50/P95/P99) cho biết phân phối: P99 latency 500ms nghĩa là 1% request chậm hơn 500ms — quan trọng hơn Mean trong SLA vì user cảm nhận "worst case" nhiều hơn trung bình.

Mental Model

Nếu 99 người đi qua cửa mất 1 giây, 1 người mất 100 giây (bị kẹt), Mean sẽ là ~2 giây — nghe "không tệ", nhưng Median vẫn là 1 giây (đúng thực tế đa số), còn P99 sẽ lộ ra chính người bị kẹt 100 giây đó — đây là insight mà Mean một mình che giấu.

Ví dụ
// BenchmarkDotNet config để show percentile
[Config(typeof(Config))]
public class MyBenchmark {
    private class Config : ManualConfig {
        public Config() => AddColumn(StatisticColumn.P95, StatisticColumn.P99);
    }
}
Experiment

Tạo 1 workload có 5% request bị "chậm bất thường" giả lập (Thread.Sleep ngẫu nhiên), thu thập 1000 mẫu latency, tính Mean/Median/P95/P99 — quan sát Mean bị kéo lệch nhiều hơn Median dù chỉ 5% mẫu bất thường.

Benchmark

So sánh báo cáo latency của cùng 1 hệ thống dùng chỉ Mean vs dùng đầy đủ P50/P95/P99 — chỉ ra Mean một mình có thể che giấu vấn đề nghiêm trọng ảnh hưởng thiểu số user.

Profiling

Công cụ load test (k6, bombardier) luôn xuất sẵn P50/P90/P95/P99 trong report — luôn đọc đầy đủ các cột này thay vì chỉ nhìn "Average Response Time".

Optimization

Đặt SLA theo P95/P99, không đặt theo Mean. Khi optimize, ưu tiên giảm P99 (worst-case) trước, vì đó thường là nguồn gốc complaint của user dù % nhỏ.

Benchmark Pitfalls Kinh Điển

Concept

Các bẫy phổ biến: (1) Dead Code Elimination — compiler tối ưu bỏ hẳn phép tính nếu kết quả không được dùng, benchmark đo "không khí"; (2) benchmark trên Debug build thay vì Release (Debug không tối ưu, số liệu vô nghĩa); (3) không kiểm soát input giống hệt nhau giữa các phương án so sánh; (4) benchmark trên máy đang chạy nhiều tiến trình nền khác gây nhiễu.

Mental Model

Dead Code Elimination giống việc bạn "đo tốc độ nấu 1 món ăn" nhưng compiler nhận ra chẳng ai ăn món đó (kết quả không dùng) nên... không nấu luôn — bạn đang đo tốc độ của sự trống rỗng.

Ví dụ
// SAI: kết quả không dùng, có thể bị tối ưu bỏ hoàn toàn
[Benchmark]
public void BadBenchmark() { var x = ExpensiveCompute(); } // x không dùng!

// ĐÚNG: return giá trị, BenchmarkDotNet đảm bảo không bị loại bỏ
[Benchmark]
public int GoodBenchmark() => ExpensiveCompute();
Experiment

Viết 1 benchmark cố tình mắc lỗi Dead Code Elimination (method void, kết quả không dùng), so sánh với bản return giá trị đúng cách — bản sai có thể cho kết quả nhanh bất thường (gần 0ns) vì thực chất không chạy gì.

Benchmark

Chạy benchmark tương tự trên build Debug vs Release, quan sát chênh lệch lớn — bài học không bao giờ tin số liệu benchmark từ Debug build.

Profiling

BenchmarkDotNet tự động cảnh báo (validator) nếu phát hiện chạy trên Debug build hoặc có debugger attached — luôn đọc kỹ warning ở đầu output trước khi tin kết quả.

Optimization

Luôn benchmark trên Release build, không có debugger attached, hạn chế process nền khác. Luôn dùng kết quả trả về (return value) trong method benchmark để tránh Dead Code Elimination.

Exercise

Review lại toàn bộ benchmark đã viết trong roadmap này, kiểm tra có mắc lỗi nào trong 4 pitfall kể trên không, sửa nếu có.

MUST KNOW

dotnet-counters

Dùng để làm gì?

Xem realtime metrics của process .NET đang chạy: CPU%, GC heap size, allocation rate, ThreadPool stats, exception count — không cần restart app, không cần instrument code.

Khi nào dùng?

Bước đầu tiên của MỌI cuộc điều tra performance — trước khi trace sâu, luôn nhìn tổng quan counters để biết nghi ngờ nên tập trung vào GC, CPU, hay ThreadPool.

Command Example
dotnet tool install --global dotnet-counters
dotnet-counters ps                             # liệt kê process .NET đang chạy
dotnet-counters monitor -p 41236                # theo dõi mặc định System.Runtime
dotnet-counters monitor -p 41236 --counters System.Runtime[gen-0-gc-count,alloc-rate]
Output Interpretation

Bảng cập nhật mỗi giây: cpu-usage (%), gc-heap-size (MB), gen-0/1/2-gc-count (cộng dồn), alloc-rate (byte/giây), threadpool-queue-length. Tăng đột biến bất thường ở bất kỳ counter nào là điểm bắt đầu điều tra.

Real-world Scenario

Production API báo latency tăng — chạy dotnet-counters trước, thấy alloc-rate tăng gấp 10 lần vào đúng giờ cao điểm → nghi ngờ có endpoint mới deploy gây allocation nặng, tiếp tục điều tra bằng dotnet-trace.

dotnet-dump

Dùng để làm gì?

Chụp lại toàn bộ trạng thái memory của process (managed + native) tại 1 thời điểm để phân tích offline — xem call stack mọi thread, object trên heap, lock đang giữ. Đặc biệt hữu ích cho deadlock/hang vì có thể chụp NGAY LÚC process đang treo.

Khi nào dùng?

Khi process bị treo (hang), crash, hoặc cần điều tra deadlock/memory leak mà không thể tái hiện dễ dàng trong môi trường dev — chụp dump từ production rồi phân tích an toàn offline.

Command Example
dotnet tool install --global dotnet-dump
dotnet-dump collect -p 41236
dotnet-dump analyze core_20260828_120000
# trong session analyze:
> clrstack -all      # call stack tất cả thread
> syncblk            # lock đang giữ — tìm deadlock
> dumpheap -stat      # thống kê object theo type
Output Interpretation

syncblk liệt kê mọi Monitor lock đang bị giữ và thread nào giữ — xâu chuỗi các thread chờ nhau để tìm chu trình deadlock. dumpheap -stat sắp xếp type theo tổng size, type chiếm nhiều memory bất thường là nghi phạm memory leak.

Real-world Scenario

Service bị treo hoàn toàn không phản hồi lúc 3 giờ sáng — trước khi restart (mất bằng chứng), chụp dotnet-dump ngay, phân tích offline sau, xác định chính xác 2 thread deadlock nhau qua lock nào.

dotnet-monitor

Dùng để làm gì?

Khi cần giám sát/chẩn đoán production liên tục mà không muốn cấp quyền exec vào container cho từng kỹ sư, hoặc muốn tự động hoá việc thu thập diagnostic data khi có sự cố (collection rules).

dotnet-gcdump

Dùng để làm gì?

Chụp snapshot riêng của GC heap (nhẹ hơn full dump vì chỉ tập trung managed object graph), phân tích object nào đang sống, ai đang giữ reference tới ai (retention path) — công cụ chính để điều tra memory leak.

Khi nào dùng?

Khi nghi ngờ memory leak (memory usage tăng liên tục không giảm dù đã qua nhiều GC cycle) — cần biết chính xác type nào đang tích luỹ và bị giữ lại bởi ai (root path).

Command Example

dotnet-gcdump collect -p 41236
dotnet-gcdump report gcdump_20260828.gcdump

Report liệt kê type theo "Inclusive Size" (tổng size bao gồm object nó giữ reference) — type đứng đầu danh sách với size bất thường lớn là điểm bắt đầu điều tra. So sánh 2 gcdump chụp cách nhau (ví dụ 10 phút) để xem type nào tăng liên tục — dấu hiệu leak rõ ràng.

EventPipe & ETW

Dùng để làm gì?

EventPipe là cơ chế cross-platform (Windows/Linux/macOS) của .NET để phát ra diagnostic event (GC, JIT, exception, custom EventSource) — nền tảng bên dưới cho toàn bộ dotnet-trace/dotnet-counters/dotnet-monitor. ETW (Event Tracing for Windows) là cơ chế tương đương chỉ trên Windows, tích hợp sâu hơn với OS-level event (kernel, driver) — PerfView dùng ETW trên Windows.

Khi nào dùng?

Hiếm khi tương tác trực tiếp — hiểu EventPipe/ETW giúp bạn hiểu CÁCH các tool ở trên hoạt động bên dưới, và cần thiết khi muốn viết custom EventSource để phát ra metric riêng của ứng dụng.

Command Example
// custom EventSource để phát metric riêng
[EventSource(Name = "MyApp")]
public sealed class MyAppEventSource : EventSource {
    public static readonly MyAppEventSource Log = new();
    [Event(1)] public void OrderProcessed(int orderId) => WriteEvent(1, orderId);
}
// dotnet-trace collect --providers MyApp
Output Interpretation

Custom event xuất hiện trong trace file y hệt built-in event, xem được qua PerfView/Speedscope — cho phép correlate business event (ví dụ "order processed") với system event (GC pause) trên cùng timeline.

Real-world Scenario

Cần chứng minh 1 GC pause cụ thể trùng đúng lúc xử lý order lớn — viết custom EventSource phát event ở đầu/cuối xử lý order, trace cả 2 loại event cùng lúc để overlay trên timeline, chứng minh nhân quả trực quan.

Exercise

PerfView

Dùng để làm gì?

Allocation-free Programming · Zero-copy · Pooling

Concept

Tổng hợp lại toàn bộ kỹ thuật đã học (struct, Span, ArrayPool, ValueTask) thành 1 tư duy thiết kế xuyên suốt: hot path không nên tạo garbage mới cho mỗi lần chạy — mọi buffer, object trung gian nên được tái sử dụng (pool) hoặc sống trên stack (struct/Span) thay vì heap. Zero-copy nghĩa là dữ liệu di chuyển qua các lớp xử lý (network → parse → business logic) mà không bị copy lại nhiều lần không cần thiết.

Mental Model

Giống dây chuyền sản xuất không rác thải (zero-waste manufacturing) — mọi vật liệu (memory) đều được tái sử dụng theo vòng tuần hoàn khép kín thay vì "dùng một lần rồi vứt" (allocate rồi để GC dọn).

Ví dụ
// pipeline zero-copy: đọc socket → parse trực tiếp trên buffer, không copy ra string
Span<byte> buffer = ArrayPool<byte>.Shared.Rent(4096);
int n = socket.Receive(buffer);
ParseHeader(buffer[..n]); // parse trực tiếp trên Span, không allocate string trung gian

Optimization

Concept

Mental Model

[DllImport("libc", EntryPoint = "getpid")]

}

Lock-free Concepts · Cache Locality · False Sharing

Concept

Lock-free programming dùng Interlocked/CAS (Compare-And-Swap) thay vì lock để đồng bộ, tránh hoàn toàn chi phí kernel-level blocking. False sharing là hiện tượng 2 biến độc lập nhưng nằm trên cùng 1 cache line (64 byte) — khi 2 thread khác nhau ghi vào 2 biến đó, CPU phải invalidate cache line qua lại giữa các core dù về mặt logic 2 biến không hề liên quan, gây chậm nghiêm trọng không rõ nguyên nhân nếu không biết khái niệm này.

Mental Model

False sharing giống 2 người làm việc ở 2 đầu 1 tờ giấy A4 chung (cache line) — dù họ viết vào 2 góc hoàn toàn khác nhau, mỗi lần 1 người viết, người kia phải "đợi lấy lại tờ giấy" (cache invalidation) dù nội dung họ quan tâm chẳng hề bị động tới.

Ví dụ
// false sharing tiềm ẩn: 2 counter của 2 thread khác nhau nằm sát nhau trong memory
struct Counters { public long CounterA; public long CounterB; } // dễ chung cache line

// sửa: pad để đảm bảo mỗi counter chiếm riêng 1 cache line (64 byte)
[StructLayout(LayoutKind.Explicit, Size = 64)]
struct PaddedCounter { [FieldOffset(0)] public long Value; }
Experiment

2 thread liên tục increment 2 biến long riêng biệt nằm sát nhau trong 1 struct (dễ false sharing) vs 2 biến đã được pad cách nhau đủ 1 cache line — đo throughput, chênh lệch có thể tới vài lần dù logic giống hệt.

Benchmark

BenchmarkDotNet với 2 thread chạy song song (dùng [Benchmark] kết hợp Parallel hoặc Task riêng) đo throughput increment/giây giữa bản có padding và không padding.

Profiling

perf stat (Linux) với counter cache-misses hoặc chuyên sâu hơn perf c2c (cache-to-cache) trực tiếp phát hiện false sharing pattern trong hardware event.

Optimization

Chỉ áp dụng padding cho các biến counter/state thực sự bị truy cập đồng thời từ nhiều thread khác nhau ở tần suất cao (hot path multi-thread) — với hầu hết code thông thường, false sharing không đáng lo.

Logs vs Metrics vs Traces vs Profiling — Khác Nhau Thế Nào

Concept

Logs là bản ghi rời rạc từng sự kiện có ngữ cảnh chi tiết ("order 123 failed: timeout") — tốt để điều tra 1 sự kiện cụ thể, tốn chi phí lưu trữ nếu log quá nhiều. Metrics là số liệu tổng hợp theo thời gian (request/s, error rate) — rẻ để lưu trữ dài hạn, tốt để phát hiện xu hướng/alert nhưng mất chi tiết từng request riêng lẻ. Traces (distributed tracing) theo dõi hành trình 1 request xuyên qua nhiều service — trả lời "request này đi qua đâu, chỗ nào chậm". Profiling (đã học Phase 9) là công cụ đào sâu NHẤT nhưng chỉ dùng được tại 1 thời điểm/process cụ thể, không chạy 24/7 vì overhead.

Mental Model

4 tầng này giống hệ thống y tế: Metrics là máy đo nhịp tim đeo hàng ngày (rẻ, liên tục, phát hiện bất thường). Logs là bệnh án ghi chi tiết mỗi lần khám. Traces là bản đồ đường đi của 1 tín hiệu thần kinh cụ thể qua nhiều bộ phận cơ thể. Profiling là chụp MRI chuyên sâu — chỉ làm khi thực sự cần, không làm hàng ngày vì tốn kém.

Ví dụ
// 1 request thực tế thường cần cả 4 tầng phối hợp:
// Metric báo error rate tăng → Log cho biết lỗi cụ thể là gì
// → Trace cho biết lỗi xảy ra ở service nào trong chuỗi gọi

MUST KNOW

OpenTelemetry · Distributed Tracing · Correlation ID

Concept

OpenTelemetry (OTel) là chuẩn mở, vendor-neutral cho việc thu thập logs/metrics/traces, tích hợp sẵn với ASP.NET Core qua Activity/ActivitySource (đã có built-in trong .NET, không cần thư viện ngoài để tạo trace). Mỗi request xuyên nhiều service cần 1 Correlation ID (thường gọi TraceId trong OTel) được truyền qua HTTP header giữa các service để nối các log/span rời rạc thành 1 bức tranh hoàn chỉnh.

Mental Model

Correlation ID giống 1 mã vận đơn theo suốt hành trình 1 gói hàng qua nhiều trạm trung chuyển (service) khác nhau — mỗi trạm ghi log riêng nhưng đều gắn cùng 1 mã, để cuối cùng bạn tra cứu được toàn bộ hành trình chỉ bằng 1 mã đó.

Ví dụ
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation()
        .AddOtlpExporter());

// tạo custom span thủ công khi cần
using var activity = MyActivitySource.StartActivity("ProcessOrder");
activity?.SetTag("order.id", orderId);
Experiment

Cấu hình OpenTelemetry cho 1 API gọi tới 1 API khác (2 service), xuất trace ra console exporter, xác nhận cả 2 service ghi trace với cùng TraceId, xem được toàn bộ hành trình request qua cả 2.

Benchmark

Đo overhead CPU/latency mà OpenTelemetry instrumentation thêm vào mỗi request — thường rất nhỏ (vài % ) nếu cấu hình sampling hợp lý, đáng đánh đổi lấy khả năng quan sát.

Profiling

Xuất trace ra 1 backend thật (Jaeger/Zipkin chạy local qua Docker, hoặc Grafana Tempo) để xem UI trace waterfall trực quan — nhìn thấy rõ span nào (DB call, HTTP call ra ngoài) chiếm nhiều thời gian nhất trong 1 request.

Optimization

Sampling hợp lý (không trace 100% traffic ở hệ thống lớn), thêm tag có ý nghĩa business (order id, user id) vào span để trace hữu ích khi điều tra thay vì chỉ có tên method.

Exercise

SHOULD KNOW

Latency · Throughput · Error Rate · Saturation

Concept

Đây là 4 chỉ số cốt lõi để đánh giá sức khoẻ 1 service (kết hợp 2 khung phổ biến: RED — Rate/Errors/Duration cho request-driven service, và USE — Utilization/Saturation/Errors cho resource). Latency (Duration) thời gian xử lý 1 request. Throughput (Rate) số request/giây. Error rate tỉ lệ request lỗi. Saturation mức độ "đầy tải" của resource (CPU, memory, ThreadPool queue, connection pool) — saturation cao là tín hiệu cảnh báo SỚM trước khi latency/error thực sự tăng.

Mental Model

Giống theo dõi 1 con đường cao tốc: Throughput là số xe/phút đi qua, Latency là thời gian đi hết đường, Error rate là số xe gặp tai nạn, Saturation là % làn đường đang bị chiếm dụng — saturation gần 100% báo hiệu tắc đường SẮP xảy ra, trước khi bạn thực sự thấy latency (thời gian đi) tăng lên.

Ví dụ
// map trực tiếp sang các counter đã học ở Phase 9:
// Throughput  ← request count / giây (custom metric hoặc log)
// Latency     ← P50/P95/P99 response time
// Error rate  ← số response 5xx / tổng request
// Saturation  ← threadpool-queue-length, gc-heap-size / limit, CPU %
Experiment

Xây 1 dashboard đơn giản (Grafana hoặc console) hiển thị đủ 4 chỉ số cho 1 API đang chạy load test, quan sát Saturation (threadpool-queue-length) tăng TRƯỚC khi Latency/Error rate bắt đầu tăng rõ rệt.

Benchmark

Load test tăng dần traffic từng bước, ghi lại điểm "gãy" (knee point) nơi Latency bắt đầu tăng phi tuyến — đối chiếu với Saturation tại đúng thời điểm đó để xác nhận mối liên hệ.

Profiling

Kết hợp dotnet-counters (Saturation nội bộ .NET) với metrics tầng hạ tầng (CPU/memory container qua Prometheus node-exporter) để có bức tranh Saturation đầy đủ cả ứng dụng lẫn hạ tầng.

Optimization

Đặt alert dựa trên Saturation (cảnh báo sớm) thay vì chỉ dựa trên Error rate (cảnh báo muộn, khi user đã bị ảnh hưởng). Đây là nguyên lý cốt lõi của SRE thực hành.

Exercise
