Bối cảnh nghiệp vụ

Một sàn TMĐT tổ chức flash sale 2 tiếng/ngày. Trong khung giờ đó lượng order dồn về gấp ~50 lần ngày thường. Mày build backend order-processing engine cho đợt này — dạng batch simulate, không cần network/DB thật.

  • Catalog: 500 sản phẩm, mỗi sản phẩm có giá gốc + tồn kho ngẫu nhiên.
  • Discount: mua ≥ 5 sản phẩm/đơn giảm 10%; khách VIP giảm thêm 5% (cộng dồn).
  • Simulate 2.000.000 order request đổ về liên tục trong 1 lần chạy.

Chức năng bắt buộc

  1. Order intake — parse 1 dòng request dạng text kiểu message queue: "CUS10293|PRD00045|3|VIP" (customerId|productId|quantity|tier).
  2. Pricing engine — tính giá cuối theo rule discount ở trên.
  3. Inventory check & deduct — đủ tồn kho thì trừ kho, không đủ thì reject (ghi log riêng, không crash).
  4. Transaction record — mỗi order thành công tạo 1 record: OrderId, CustomerId, ProductId, Quantity, FinalPrice, Timestamp.
  5. Notification fan-out — mỗi giao dịch thành công phải bắn event cho 3 subsystem giả lập: WarehouseService, InvoiceService, AnalyticsService.
  6. Payment Gateway connection — mỗi order khi thanh toán phải mở 1 "connection" giả lập (object nắm giữ tài nguyên) và đóng lại sau khi dùng.
  7. End-of-sale report — kết thúc thì gom dữ liệu (tổng doanh thu, top 10 sản phẩm bán chạy, số đơn reject) vào 1 buffer rồi in ra.

Cách làm: bắt buộc 2 vòng

Vòng 1 — Naive

Viết theo bản năng, ưu tiên đúng nghiệp vụ, không cần tối ưu. Cho phép (thậm chí khuyến khích) cố ý mắc lỗi kinh điển: class cho OrderItem/Money, ArrayList/object ở đâu đó, nối string trong vòng lặp, quên gỡ event ở bước 5, không Dispose đúng ở bước 6.

ĐO BASELINE

  • Tổng thời gian xử lý 2 triệu order
  • Tổng byte allocated
  • Số lần GC theo từng Gen
  • Bộ nhớ cuối, có tăng dần qua 5 lượt "flash sale" lặp lại trong 1 process không (phép thử leak)

Vòng 2 — Optimized

Áp dụng đúng kỹ thuật value/reference type · stack/heap · object lifetime, sửa từng chỗ đã cố ý làm sai ở vòng 1:

  • OrderItem / Money → readonly struct
  • Parse request line → ReadOnlySpan<char>, không Split/Substring
  • Loại boxing (bỏ ArrayList/object, tier dùng enum không box khi làm key)
  • Payment Gateway connection → IDisposable + using đúng chuẩn
  • Notification fan-out → gỡ event đúng chỗ, không leak
  • Report buffer cuối kỳ → StringBuilder/ArrayPool thay vì nối string

ĐO LẠI

  • Đúng các chỉ số như vòng 1, để so sánh trực tiếp

Deliverable

Code (2 phiên bản naive + optimized) + 1 file báo cáo report.md theo đúng cấu trúc:

  1. Tóm tắt bối cảnh nghiệp vụ (vài dòng)
  2. Bảng số liệu đo NAIVE
  3. Phân tích nguyên nhân — mỗi vấn đề chỉ rõ dòng code nào gây ra, quy về đúng khái niệm (value/reference type, stack/heap, object lifetime), không nói chung chung "chậm"
  4. Giải pháp OPTIMIZED cho từng vấn đề đã nêu ở mục 3
  5. Bảng số liệu đo OPTIMIZED
  6. Bảng so sánh % cải thiện (thời gian / allocated bytes / GC count / memory cuối)
  7. Kết luận & trade-off nếu có (VD: readonly struct có làm code kém tiện chỗ nào, Span có giới hạn gì trong domain này không)

Ràng buộc

  • .NET 8+, chỉ xuất qua Console.WriteLine — không file/DB/network thật.
  • Không gọi GC.Collect() thủ công trong bản OPTIMIZED trừ khi dùng để đo leak (và phải ghi rõ trong report vì sao).
